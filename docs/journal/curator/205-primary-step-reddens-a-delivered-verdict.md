# Тред 205 — чем curator читает дифф воркфлоу, когда круга ревью не будет

Запись такта 2026-09-14 по треду `205-primary-step-reddens-a-delivered-verdict`. Предмет треда —
починка dev-core (PR #433): круг ревью, который вердикт ВЫНЕС и ДОСТАВИЛ, перестаёт краснеть от
падения шага ревьюера. Кнопка по такому PR — john (гард 4, `.github/workflows/**`), метка `review`
на него не вешается (действие самопропускается по построению), и гард 1 закрывается ЧЕЛОВЕЧЕСКИМ
чтением. Ниже — то, чем это чтение удешевляется, и что из этого меняет поведение роли.

## 1. Дифф `continue-on-error` судится ТРЕМЯ грепами по голове PR, а не чтением двух добавленных строк

`continue-on-error: true` меняет `conclusion` шага и не трогает `outcome`. Отсюда два класса
читателей, и опасен ВТОРОЙ, потому что его в диффе не видно вовсе:

1. `steps.<id>.outcome` — читатели НЕ затронуты (результат ДО применения);
2. `steps.<id>.conclusion`, `failure()`, `job.status` — читатели ПЕРЕВОРАЧИВАЮТСЯ: шаг с
   `if: failure()` после такой строки перестанет запускаться, и дифф об этом молчит.

Замер на голове `e12a407128889dcde398e68d6d3a6162e70a06cf` (файл взят `gh api … contents/…?ref=<sha>`,
дерево не трогалось):

- `grep -n 'continue-on-error'` → три места: 261 (`reviewer`), 704 (`reviewer_fallback`), 1379
  (артефакт транскрипта, был и остался);
- `grep -n 'failure()\|job\.status\|\.conclusion'` → **одно** попадание, и оно не про шаги: строка
  193 — `jq` по `.jobs[].conclusion` ЧУЖОГО прогона (перепись `checks`). Читателей второго класса в
  файле НЕТ;
- `grep -n 'steps\.reviewer'` → `outcome` читают ровно двое: `PRIMARY_OUTCOME` шага `limit` (586) и
  `FALLBACK_OUTCOME` шага `reviewer_out` (734).

**Правило роли:** прежде чем звать `continue-on-error` безопасным, ищи читателей `conclusion`,
`failure()` и `job.status` по ВСЕМУ файлу. Отсутствие попаданий — факт, а «шаг ниже всё равно
`!cancelled()`» — рассуждение.

## 2. Дифф без единой строки удаления — даровой оракул «запретов не снято»

`gh pr view 433 --json files` дал `275 insertions(+)`, удалений ноль по всем четырём файлам. Для
гарда 3 в части «новой нормы не вводит» половина вопроса («снятие или сужение существующего
запрета») закрывается этим числом целиком: снять запрет, ничего не удалив, нельзя. Остаётся сверить
только добавленное. Одна команда вместо чтения четырёх файлов.

## 3. «Сюита зелёная» у ЧУЖОГО прогона проверяется СЧЁТОМ состояний, а не цветом джобы

Интеграционная сюита доставки умеет пропустить состояния молча (нет PyYAML — нет разбора `.yml`),
и джоба при этом зелёная. Поэтому цвет `checks` не доказывает, что новые состояния вообще
исполнялись. Оракул — строка счёта в логе прогона:

```
gh run view <id> --log | grep -a 'СОСТОЯНИ'
→ интеграционный прогон доставки: ВСЕ СОСТОЯНИЯ ПРОШЛИ — 27 шт.
```

27 на прогоне `34851787658` (голова `e12a407…`) — столько же, сколько исполнитель намерил рукой,
то есть состояния (23)–(26) проехали В CI, а не только на его ящике. Вывод в контекст не едет:
`grep` оставляет одну строку.

## 4. Два PR, дописывающих ОДИН файл-список, конфликтуют — и это мерится ДО мёржа, обоими головами

#431 (тред 201) и #433 (тред 205) трогают `.github/workflows/claude-review.yml` и
`.github/scripts/review-delivery.integration.sh`. Оба показаны GitHub как `MERGEABLE` — потому что
каждый мержабелен С MAIN, а не друг с другом. Замер:

```
git fetch origin pull/431/head:refs/tmp/… pull/433/head:refs/tmp/…
git merge-tree --write-tree --name-only refs/tmp/…/pr431 refs/tmp/…/pr433
→ CONFLICT (content): .github/scripts/review-delivery.integration.sh
  (claude-review.yml при этом слился сам)
```

**Правило роли:** `mergeable: MERGEABLE` у двух открытых PR НЕ значит, что они не столкнутся; когда
оба дописывают нумерованный список (состояния сюиты, таблица, хвост дока), конфликт нужно мерить
`merge-tree` по двум головам — заранее, чтобы объявленный порядок мержа знал СВОЮ цену, а не узнавал
её от GitHub после первой кнопки. Здесь порядок был объявлен в постановке (§4: #431 первым,
ребейз платит #433), и замер говорит, что вторая кнопка будет не бесплатной ни в каком порядке:
платит тот, кто второй.

## 5. Чего этот такт НЕ делал

Кнопки нет: `merge-gate --pr 433` печатает `STOP guard 4` («john merges this one — it changes
.github/workflows/claude-review.yml») и `STOP guard 1` («no approve verdict on e12a407» — круга не
будет по построению). Гард 2 — `ok` (`checks=SUCCESS` на той же голове) с нотой переезда базы.
Гард 3 восходит к слову john 2026-09-14 ~13:27Z (доставка в тред `180-selfheal-leaves-the-workspaces-behind`,
`msg-138`): «ДЕЛАЙ ОБЕ ПОЛОВИНЫ. Ставь `dev-core` тредом на воркфлоу; кнопка мержа его».
Чтение выше — чтение curator, и гарда 1 оно НЕ закрывает: его закрывает человек, названный в треде
поимённо.
