# Ввод ящика в строй

Одна страница копипаст-блоков: как поднять НОВУЮ машину, которая будет держать роли
контура без участия человека. Постановка — тред `019-operator-ux` (решение john,
2026-07-31): **постановка ящика — команды CLI, а не переписка с координирующей ролью.**

**Критерий готовности ровно один: `doctor` зелёный.** Не «кадр выглядит нормально»,
не «демон вроде поднялся» — строка `doctor: green` в конце чек-листа. Приёмочный
норматив — пройти эту страницу сверху вниз за ≤15 минут.

Порядок неслучаен и его не переставляют: **гигиена ОС → репозиторий и Node → `init` →
`doctor` → демон резидентом**. Каждый следующий шаг проверяется предыдущим; `init`
кончается доктором сам, поэтому отдельно его звать не нужно.

---

## 0. Системная гигиена ОС — РАЗДЕЛ ПУСТ

apt/пользователь `runner`/ufw/sshd/Docker для self-hosted раннеров.

**Материала здесь нет** — он у того, кто ставил ОС этого ящика, и в текст пока не
выгружен. Раздел оставлен пустым НАЗВАННОЙ дырой, а не молчанием: пустой раздел
видно, а отсутствующий читается как «этого шага нет».

Что известно про него по факту (для того, кто будет писать): CLI сюда не лезет по
построению — ему не нужен root. Отдельно про раннеры: пользователь раннера обязан
состоять в группе `docker` **и сервисы раннеров после `usermod -aG` перезапускаются** —
на уже запущенный процесс членство в группе не действует, и `checks` падает
`docker: command not found` (exit 127) при полностью настроенной группе.

## 1. Репозиторий и Node

```bash
git clone <origin> ~/projects/language-learning-ecosystem
cd ~/projects/language-learning-ecosystem
nvm install "$(cat .nvmrc)" && nvm use          # Node 24; corepack идёт в комплекте
corepack enable
pnpm install                                    # ОБЯЗАТЕЛЬНО: без node_modules нет tsx,
                                                # а значит нет и самого CLI протокола
```

`pnpm install` здесь не «на всякий случай»: CLI протокола запускается через `tsx`,
и на ящике без `node_modules` любая команда ниже не существует. Это один из
регресс-сценариев вечера 2026-07-31.

Дальше все команды — из корня репозитория:

```bash
pnpm -F agent-protocol cli <команда>
```

**Подпись коммитов ящика — сразу, одной строкой.** Рабочие места ролей и доставку
почты пакет подписывает сам (роль на каждый коммит), но у ящика остаются коммиты,
которые делает не он: руками в чекауте почты, служебные в основном чекауте,
что-нибудь под пользователем-демоном. Их подпись берётся из общего конфига git, и
если он не задан — из имени хоста, откуда в истории и завелись `curator@lle.local`,
`dev-core@agents.local` и прочие «вторые dev-core». Канон и словарь авторизованных
identity — в документе, который проект объявляет в своём конфиге полем
`identityDictionary`; на ящике:

```bash
git config --global user.name  "agent-protocol"
git config --global user.email "orchestrator@agents.invalid"
```

Это подпись **машинерии**, а не роли, и это правда: коммит, сделанный на ящике не
сессией, сделала машина. Роль поверх неё ставится на каждый коммит и ничего не
теряет. Проверяют две строки `git: commit identity` в `doctor` (шаг 5): `(history)` —
кто подписал историю, `(this box)` — чем подпишет следующий коммит ЭТОТ ящик. На
свежей коробке важна вторая: своих коммитов у неё ещё нет, и первая промолчит.

## 2. Файл секретов транспорта

Отдельным блоком намеренно: это единственное на ящике, что **не делает ни одна
команда**. `init` записывает в машинный конфиг только ПУТЬ к файлу, сам файл кладёт
человек — и порядок «сперва сказать где, потом положить» штатный: конфиг держит путь
к ещё не существующему файлу и говорит об этом строкой, а не отказом.

```bash
mkdir -p ~/.config/agent-protocol
umask 077
cat > ~/.config/agent-protocol/secrets.env <<'EOF'
TELEGRAM_BOT_TOKEN=<токен бота>
TELEGRAM_CHAT_ID=<id чата>
EOF
chmod 600 ~/.config/agent-protocol/secrets.env
```

- Имена ключей — транспорта (`packages/transport-telegram`), не проекта; ядро
  протокола о вендоре не знает.
- Файл **вне git** и вне репозитория. В конфигах не лежат значения — только путь
  (R4/R14: репозиторий говорит ЧТО доставляется и какими словами, машина — ГДЕ лежат
  креденшлы).
- Нет файла — уведомления просто не доставляются; `init` и `doctor` об этом скажут,
  но поднимать роли ящик будет.

## 3. `init` — машинный конфиг одной командой

Сперва **план**, потом то же самое с `--write`:

```bash
# план: печатает по шагам, что запишет и что создаст
pnpm -F agent-protocol cli init \
  --instance <id-инстанса> \
  --agent claude-code --exec "$(which claude)" \
  --operator curator \
  --secrets ~/.config/agent-protocol/secrets.env

# то же самое, но по-настоящему (в конце сам гоняет doctor)
pnpm -F agent-protocol cli init \
  --instance <id-инстанса> \
  --agent claude-code --exec "$(which claude)" \
  --operator curator \
  --secrets ~/.config/agent-protocol/secrets.env \
  --write
```

Что делает и чего не делает:

| флаг | смысл |
|---|---|
| `--instance <id>` | КЕМ этот ящик себя называет (R13). Не угадывается: без флага — отказ, потому что догадка подняла бы роль чужой машины. Занятый соседом id — предупреждение с именем соседа |
| `--agent <kind> --exec <path>` | где на этой машине бинарь агента; резолв через PATH, а не набором пути руками |
| `--operator <role>` | кто сидит за ящиком: этим подписывается `hold`, набранный без `--by` |
| `--secrets <path>` | ГДЕ лежит файл секретов (см. §2). Файл не создаётся никогда |
| `--no-doctor` | остановиться на записи — для ящика, у которого ещё нет сети |
| `--offline` | не ходить в сеть (см. ниже) |

Результат — `~/.config/agent-protocol/local.json` (перекрывается `--local-config`):
`instance`, `operator`, `agents.<kind>.exec`, `secrets.envFile`. Ничего из политики
(права, потолки, модель, ветка, тексты уведомлений) машинный конфиг не несёт и
отвергает по имени — это репозиторий.

Чекаут почты создаётся **вместе с fetch**. Это не оптимизация: чекаут, сделанный
руками без fetch, читается как `mail: never pulled` в каждом кадре — ящик выглядит
введённым в строй и работает по вчерашней почте.

**Одно сетевое действие переживает план.** На ящике, где чекаута почты ещё нет,
чтение «занят ли этот id соседом» делает настоящий `git fetch` ветки почты
(`origin/<branch>` двигается, больше ничего) — иначе предупреждение о занятом id
пришло бы ПОСЛЕ того, как id занят. `--offline` от этого чтения отказывается и
говорит об этом строкой.

## 4. `init github` — identity ящика для GitHub

Ящику нужен свой ключ: демон пушит почту и ветки без человека за клавиатурой.
Это **единственный шаг ввода, который создаёт материал вне репозитория и вне обоих
конфигов** — пару ключей в `~/.ssh` и блок `Host` рядом с ней.

```bash
pnpm -F agent-protocol cli init github            # план: ничего не делает
pnpm -F agent-protocol cli init github --write    # ключ + ~/.ssh/config + ssh -T
```

**Форма identity решена (john, 2026-08-01): ключ ящика живёт DEPLOY KEY-ем
обслуживаемого репозитория, с галкой write.** Ни отдельный аккаунт, ни machine user не заводятся;
machine user — ответ только на горизонте «один ящик обслуживает несколько
репозиториев», потому что deploy key принадлежит ровно одному.

Команда печатает публичную половину и четыре клика — **выдачу доступа она не
автоматизирует**: репозиторий → Settings → Deploy keys → Add deploy key → вставить →
галка «Allow write access». Это единственный шаг всего ввода, который раздаёт права,
и он остаётся человеческим.

Три вещи, которых команда не делает, и каждую стоит знать заранее:

- **не перезаписывает существующий ключ** — какие хосты ему доверяют, на этом ящике
  неизвестно; ротация делается руками (отодвинуть файл, затем `--write`);
- **не судит по коду возврата `ssh -T`**: `ssh -T git@github.com` на РАБОЧЕМ ключе
  выходит с кодом 1 (аутентификация прошла, шелла GitHub не даёт). Вердикт читается
  из слов ответа, а слова называют **репозиторий**, который открывает deploy key, —
  это и есть нужный факт. Имя аккаунта на месте репозитория команда называет
  расхождением, а не успехом (обычно — потерянный `IdentitiesOnly yes`);
- **без `--write` не делает ничего**: ключ не генерируется, `~/.ssh` не открывается,
  GitHub ни о чём не спрашивается.

| флаг | что делает |
|---|---|
| `--key <path>` | где лежит пара (по умолчанию `~/.ssh/github`) |
| `--host <h>` | хост блока `Host` (по умолчанию `github.com`) |
| `--comment <c>` | комментарий ключа; по умолчанию — id инстанса, чтобы список deploy keys читался по ящикам |
| `--no-probe` | остановиться на identity на диске (ящик без сети); сводка честно говорит, что это ничего не доказывает |

## 5. `doctor` — чек-лист готовности

`init --write` кончается им сам; отдельно — когда ящик уже стоит:

```bash
pnpm -F agent-protocol cli doctor
```

Строки, которые он даёт (✓/✗ с причиной), и как читать кресты. Их **одиннадцать** на
обычном ящике, и «десять» — не константа: пара `agent: …` печатается на КАЖДЫЙ
объявленный worker, а `mail: checkout freshness` не печатается вовсе, если чекаута
нет (проверять нечего). Сверять вывод построчно с этой таблицей — то, для чего она
здесь; незнакомая строка в выводе значит, что устарела таблица.

| строка | крест значит |
|---|---|
| `config: repository` | конфиг протокола в репозитории не читается по указанному ref |
| `config: machine` | `local.json` не парсится — имя неизвестного ключа названо |
| `config: instance` | ящик без имени при объявленных в репозитории инстансах — **он не поднимет никого**; чужой/необъявленный id — не ошибка, а «стенд: ролей этого проекта не поднимает» |
| `agent: binary (<worker>)` | бинарь не найден в PATH **дочернего процесса** (PATH демона и PATH сессии — разные вещи): спавн упал бы с уже взятой арендой. Лечится объявлением пути в машинном конфиге — `agents['<worker>'].exec`; строка называет и слой, откуда путь взят (флаг / машинный конфиг / умолчание) |
| `agent: headless run (<worker>)` | бинарь есть, а живого `-p`-прогона нет: креденшлы в домашнем каталоге протухли. Это отказ, который снаружи больше всего похож на успех — демон поднимает сессии, каждая умирает на первом вызове |
| `git: origin` | нет remote `origin`; url печатается замаскированным (токен в url не выводится — правило 10) |
| `git: fetch` | чтение из origin не проходит |
| `git: write access (dry-run push)` | ящик читает, но не пишет: сессия умрёт на ПОСЛЕДНЕМ шаге — на доставке, уже сделав работу |
| `mail: checkout` | чекаута почты нет вовсе — вопрос про ЯЩИК, а не про прогон: создать worktree **с fetch** (созданный без него читается как «никогда не тянули») |
| `git: commit identity (history)` | адрес внутри `@agents.invalid`, которому не отвечает ни одна объявленная роль: какой-то ящик подписывается несуществующей ролью. Чужой адрес крестом НЕ является — он назван точкой со счётом коммитов, и судить его надо по словарю канона — тому документу, который проект объявляет полем `identityDictionary` своего конфига; окно — `--identity-window <days>` (7 по умолчанию), вся история — `--identity-all`. Строка локальная: `--offline` её не отключает. **Словаря может не быть**: он едет с ИНСТРУМЕНТОМ, а строка спрашивает про обслуживаемый проект — тогда обе identity-строки называют его отсутствие фактом в той же фразе (вердикт не меняется: отсутствие словаря — свойство репозитория, а не подписи ящика) |
| `git: commit identity (this box)` | вторая половина того же вопроса и та, ради которой шаг стоит в приёмке коробки: чем ЭТОТ ящик подпишет СЛЕДУЮЩИЙ коммит. Спрашивается `git config --get user.email` в чекауте, в чекауте почты и в рабочем месте каждой роли. **Пусто — крест**: git молча выведет `<user>@<hostname>`, откуда и взялись `@lle.local`/`@agents.local` (на хосте без домена git вместо этого откажется коммитить — потому дефект и не воспроизводился на дев-машине). Второй крест — тот же самозванец внутри `@agents.invalid`; всё остальное точка. Строка тоже локальная и `--offline` её не отключает |
| `mail: checkout freshness` | чекаут есть, но не годен: сидит на чужой ветке, грязный или с неотправленными коммитами. Строку выдаёт тот же судья, которым демон отказывает в запуске (`mailCheckoutVerdict`) — крест здесь и отказ демона это одна фраза, а не две похожие. Появляется только если предыдущая строка зелёная |

Команда **ходит в сеть и тратит один вызов агента** — в этом её смысл: этих фактов
нет ни в одном файле. `--offline` оставляет их незаданными и говорит об этом в
строках, но никогда не выдаёт за пройденные. `--probe-timeout <sec>` — потолок
сетевых проб.

Развилка, о которой стоит знать заранее: в организации могут быть **выключены deploy
keys политикой** — тогда право записи даётся не ключом репозитория, а аккаунтом или
machine user, и строка `git: write access` красная при полностью правильном ключе.

## 6. Демон резидентом

Юнит **генерируется с этого ящика** (репозиторий, этот интерпретатор, путь к CLI):
юнит, набранный руками на каждой машине, — первое, что протухает.

```bash
pnpm -F agent-protocol cli orchestrator systemd install            # печатает юнит и путь
pnpm -F agent-protocol cli orchestrator systemd install --write    # кладёт файл
```

**Набирать это из основного чекаута, не из рабочего места роли** (`.worktrees/<роль>`):
`WorkingDirectory` резолвится в домашний чекаут откуда угодно (R26), а `ExecStart` несёт
путь к CLI и лоадеру ТОГО дерева, в котором команду набрали, — то есть демона поднимали бы
из дерева, которое контур сам каждый пакет ставит на базу, лочит и убирает (R17). Юнит при
этом выглядит правильным и ломается позже. Команда такой запуск **отклоняет** (exit 2) и
называет три вещи: чьё это рабочее место (роль), почему резидентный юнит из него нельзя и
путь основного чекаута, из которого команду надо повторить.

Признак рабочего места — объявленные `orchestrator.workdir.worktrees`, ровно тот же, что
у `zones check --role-from-workspace`. Любой ДРУГОЙ линкованный worktree (чекаут почты,
ваш собственный) команда пропускает, печатая строку-примечание: R17 такое дерево не
переставляет, и отказ там назвал бы неверную причину.

Дальше — руками, и команда сама их печатает (включение юнита и linger остаются
человеческими действиями по R14):

```bash
systemd-analyze --user verify ~/.config/systemd/user/agent-protocol.service  # ДО включения
systemctl --user daemon-reload                                  # без него systemd юнита не видит
systemctl --user reset-failed agent-protocol.service          # снимает прошлый failed и счётчик StartLimit
systemctl --user enable --now agent-protocol.service
loginctl enable-linger "$USER"
journalctl --user -u agent-protocol.service -f                # тот же поток, что в логе демона
```

Имя юнита — `agent-protocol.service`, если не задан `--unit-name`. Набирать его
с этой страницы не нужно: `systemd install` печатает все шесть строк уже с тем
именем, которое положил, — копипастить надёжнее из вывода команды, а не отсюда.

`reset-failed` стоит перед `enable --now` не для порядка: юнит, добравшийся до
потолка `StartLimitBurst`, остаётся в `failed` со полным счётчиком, и следующий старт
отказывается строкой «start request repeated too quickly» — ответом про ПРОШЛУЮ
установку, а не про эту. На юните, который ни разу не падал, команда — no-op; ставить
её после первого же неудачного старта приходится всё равно, поэтому она в списке
всегда. Ровно эта строка съела первую минуту диагностики на обкатке 2026-08-02.

Первым шагом стоит именно `systemd-analyze --user verify`, и стоит он там не для
красоты: ключ, положенный не в ту секцию, systemd не отвергает — он пишет «Unknown
key name» в журнал и работает дальше БЕЗ этой гарантии, то есть юнит выглядит
установленным, а половины его поведения нет. Обкатка 2026-08-02 на `lle-agents`
нашла ровно это (`StartLimitIntervalSec` в `[Service]`) плюс вторую половину —
голый `node` перед `.ts`-входом, отчего юнит падал первым же импортом
(`ERR_MODULE_NOT_FOUND`). Обе починены в генераторе; `ExecStart` теперь несёт
`node --import <…>/tsx/dist/loader.mjs` абсолютным путём (никакого `tsx` из PATH),
и команда печатает строкой, какой интерпретатор она положила.

Третье того же класса — **`Environment=PATH=` в юните**. Самому демону PATH не нужен
(интерпретатор назван абсолютным путём), но бинарь агента резолвится через PATH
ДОЧЕРНЕГО процесса, и `git` с `sh` — тоже; пользовательский юнит логин-шелл не
наследует. Без этой строки демон стартует, `verify` зелёный, а первый же спавн сессии
падает с уже взятой арендой. PATH собирается из фактов ящика: каталог интерпретатора,
каталоги бинарей агентов из машинного конфига (R14) и системный пол
(`/usr/local/bin:/usr/bin:/bin`). Бинарь, названный в машинном конфиге ГОЛЫМ именем,
команда резолвит вашей же оболочкой и печатает строкой, что положила; не нашла —
говорит об этом и каталог НЕ выдумывает (лечится `config set agent <kind> --exec
<абсолютный путь>`).

И `RestartPreventExitStatus=2`: код 2 — «аргументы не резолвятся» (плохой ref,
неизвестный инстанс, нечитаемый конфиг), рестартом это не лечится никогда. Без строки
юнит молотится до потолка и рапортует «repeated too quickly», то есть называет потолок
вместо причины; с ней — останавливается на первом отказе, а настоящий крэш (любой
другой код) по-прежнему рестартует.

Уровень пользовательский, не root: сессии читают машинный конфиг и креденшлы
ОПЕРАТОРА (R14).

Дальше — гейт и картинка:

```bash
pnpm -F agent-protocol cli orchestrator enable --ref origin/main --write   # без него не поднимается никто
pnpm -F agent-protocol cli orchestrator status                             # живой кадр: аренды, холды, очередь
```

`up`/`down`/`hold`/`resume`/`status` и `doctor` можно набирать без `--ref` — он берётся
из `orchestrator.ref` конфига рабочего дерева, и какой именно взят, команда печатает.

### Обкатка юнита — три вопроса, которые задают ОДИН раз на ящик

Что демон поднялся, видно сразу. Три вещи видно только через ребут и через неделю
работы, и проверять их надо намеренно (постановка john 2026-08-02: юнит обкатывается
на стенде, который ролей контура не поднимает по построению, — обкатывается **именно
юнит**).

**1. Пережить ребут.**

```bash
systemctl --user is-enabled agent-protocol.service   # enabled
loginctl show-user "$USER" -p Linger                   # Linger=yes
sudo reboot
# после ребута — НЕ открывая ssh-сессию заранее:
systemctl --user is-active agent-protocol.service    # active
pnpm -F agent-protocol cli orchestrator status         # circuit: daemon pid …, alive
```

Обе половины проверяются отдельно, потому что каждая по отдельности выглядит как
работающая: `enable` без linger даёт юнит, живущий до выхода из ssh; linger без
`enable` — юнит, который сам не стартует.

Ловушка ровно одна, и она тихая: **force-флаг, оставшийся на полу до ребута.** `up`
под юнитом отказывается стартовать по нему ЧИСТЫМ выходом (код 0) — намеренно, чтобы
`Restart=on-failure` не воевал с выключателем. Снаружи это неотличимо от «юнит просто
не поднялся»: `systemctl --user status` показывает `inactive (dead)` без единой
ошибки, а причина — одной строкой в `journalctl`. Стоп-флаг такой ловушкой НЕ
является: `up` чистит его сам и говорит об этом строкой.

**2. Ротация логов.** Демон пишет в `<repo>/.orchestrator/daemon.log` (каталог —
`orchestrator.state` конфига). Ротация происходит **на старте**: файл больше потолка
(8 МБ по умолчанию) уезжает в `daemon.log.1`, одна генерация, без cron и без
logrotate. Каждый старт кладёт баннер `=== daemon epoch · <ts> · pid N · foreground ===` —
по нему читается, чей это кусок лога.

Ждать 8 МБ, чтобы это проверить, не нужно — потолок вшивается в юнит:

```bash
# --daemon-args ЗАМЕЩАЕТ аргументы юнита целиком, а не дополняет: ref возвращается руками
pnpm -F agent-protocol cli orchestrator systemd install \
  --daemon-args '--ref origin/main --log-max-bytes 65536' --write
systemctl --user daemon-reload && systemctl --user restart agent-protocol.service
# дать демону натикать за потолок (несколько тиков), затем ещё один restart:
ls -l ~/projects/language-learning-ecosystem/.orchestrator/daemon.log*   # появился .log.1
grep -c '=== daemon epoch' ~/projects/language-learning-ecosystem/.orchestrator/daemon.log
```

Под юнитом первичный канал — journald (он ротируется сам); этот файл — зеркало, и
потолок нужен именно ему. После обкатки потолок из юнита убирают тем же
`systemd install --write` без `--daemon-args`.

**3. Честный кадр на стенде.** Ящик, объявленный в `instances` репозитория с пустым
списком ролей, — **стенд**, и это не ошибка: `doctor` даёт по нему точку («a bench: it
raises no role of this project»), вердикт остаётся зелёным, а `status` называет каждую
невзятую роль причиной `owned by instance '<id>', this box is '<id>'`. Пустая очередь
без причин была бы неотличима от «почты нет» — потому причины и печатаются.

Ключевое слово здесь — **объявленный**: честный кадр бездействия предполагает имя,
которое репозиторий знает. Ящик, назвавшийся именем, которого в `instances` нет, —
не стенд, а отказ на двери (R13: «машина без имени или с чужим именем при объявленной
топологии не поднимает никого»), и лечится он PR в конфиг, а не флагом. Обкатка
2026-08-02 упёрлась именно в это: страницу писали про ящик, который на тот час ещё не
был объявлен, и она обещала кадр, недостижимый по построению.

Одного стенд не отменяет: **строки `agent: binary` и `agent: headless run` судятся и
на нём**, а вторая ходит живым `-p`-прогоном в креденшлы того пользователя, под
которым стоит юнит. Ящик без креденшлов даёт по ней крест, и критерий приёмки
«`doctor` зелёный» упрётся именно в него. Это не дефект строки: она ровно про то,
поднимет ли этот ящик сессию, — но на стенде её стоит закрывать первой, а не
последней.

## 7. Сторож ящика — ВНЕ GitHub, и это его смысл

**Постановка john, тред 019 → 049, пункт 4.** За контуром на ящике следит `Notifier
Watch` — но он живёт в GitHub Actions и умеет видеть только отказ прогона. Ящик,
который выключили, у которого кончилось место или который не пережил ребут, ему не
виден вовсе: молчащий ящик ничем не отличается от тихого дня. Сторож поэтому стоит
СНАРУЖИ — то, что следит за машиной, не может исполняться на этой машине.

Форма — самая дешёвая из работающих: cron на ящике пингует внешний счётчик, счётчик
молчание превращает в алерт.

### Разовая настройка (руки владельца решения — сейчас john)

1. Завести чек на [healthchecks.io](https://healthchecks.io) (бесплатного плана
   хватает): period — **10 минут**, grace — **10 минут**. Смысл пары: пинг раз в
   5 минут, тревога — после двадцати минут тишины, то есть после четырёх пропущенных
   подряд, а не после одного лага cron.
2. В интеграциях чека подключить **Telegram** и указать тот же чат, куда протокол
   шлёт уведомления (`TELEGRAM_CHAT_ID` из файла секретов транспорта, §2). Токен бота
   healthchecks просит свой — это его канал, не наш; секреты протокола ему не отдаём.
3. URL пинга положить в файл секретов транспорта рядом с остальными (§2), ключом
   `HEALTHCHECKS_URL` — он такой же секрет, как токен: кто его знает, тот может
   заглушить тревогу.

### Строка cron

```bash
# crontab -e  (от ОПЕРАТОРА, не от root: файл секретов — его, §2)
*/5 * * * * . "$HOME/.config/agent-protocol/secrets.env"; curl -fsS -m 10 --retry 3 "$HEALTHCHECKS_URL" >/dev/null
```

Путь к файлу секретов — тот, что назван `secrets.envFile` в машинном конфиге
(`~/.config/agent-protocol/local.json`); если он другой, подставить его.

Проверка — не «строка добавилась», а **факт на той стороне**: на дашборде чека
появился пинг, и после `crontab -e` с закомментированной строкой через 20 минут
пришёл алерт в Telegram. Сторож, тревогу которого ни разу не видели, ничем не
отличается от выключенного.

### Чего этот сторож НЕ делает

Он отвечает ровно на один вопрос — «ящик жив». Он не знает ни про демона (живой ящик
с упавшим юнитом пингует исправно), ни про место на диске, ни про очередь. Расширять
пинг условиями («пингуй, только если `is-active`») — соблазн, который стоит назвать и
не трогать: сторож, у которого есть своя логика, отказывает вместе с ней, а его
собственный отказ никому не виден по построению. Живость демона — вопрос кадра
`orchestrator status` и `Restart=on-failure` юнита (§6), не этого cron.
