# Ввод ящика в строй

Одна страница копипаст-блоков: как поднять НОВУЮ машину, которая будет держать роли
контура без участия человека. Постановка — тред `019-operator-ux` (решение john,
2026-07-31): **постановка ящика — команды CLI, а не переписка с curator.**

**Критерий готовности ровно один: `doctor` зелёный.** Не «кадр выглядит нормально»,
не «демон вроде поднялся» — строка `doctor: green` в конце чек-листа. Приёмочный
норматив — пройти эту страницу сверху вниз за ≤15 минут.

Порядок неслучаен и его не переставляют: **гигиена ОС → репозиторий и Node → `init` →
`doctor` → демон резидентом**. Каждый следующий шаг проверяется предыдущим; `init`
кончается доктором сам, поэтому отдельно его звать не нужно.

---

## 0. Системная гигиена ОС — РАЗДЕЛ ПУСТ

apt/пользователь `runner`/ufw/sshd/Docker для self-hosted раннеров.

**Материала у dev-core нет** — он в рабочей сессии john (тред 019: «системная гигиена
ОС … можно выгрузить из сегодняшней сессии, у john всё в чате»). Раздел оставлен
пустым НАЗВАННОЙ дырой, а не молчанием: пустой раздел видно, а отсутствующий читается
как «этого шага нет».

Что известно про него по факту (для того, кто будет писать): CLI сюда не лезет по
построению — ему не нужен root. Отдельно про раннеры: пользователь раннера обязан
состоять в группе `docker` **и сервисы раннеров после `usermod -aG` перезапускаются** —
на уже запущенный процесс членство в группе не действует, и `checks` падает
`docker: command not found` (exit 127) при полностью настроенной группе.

## 1. Репозиторий и Node

```bash
git clone <origin> ~/projects/language-learning-ecosystem
cd ~/projects/language-learning-ecosystem
nvm install "$(cat .nvmrc)" && nvm use          # Node 24; corepack идёт в комплекте
corepack enable
pnpm install                                    # ОБЯЗАТЕЛЬНО: без node_modules нет tsx,
                                                # а значит нет и самого CLI протокола
```

`pnpm install` здесь не «на всякий случай»: CLI протокола запускается через `tsx`,
и на ящике без `node_modules` любая команда ниже не существует. Это один из
регресс-сценариев вечера 2026-07-31.

Дальше все команды — из корня репозитория:

```bash
pnpm -F agent-protocol cli <команда>
```

## 2. Файл секретов транспорта

Отдельным блоком намеренно: это единственное на ящике, что **не делает ни одна
команда**. `init` записывает в машинный конфиг только ПУТЬ к файлу, сам файл кладёт
человек — и порядок «сперва сказать где, потом положить» штатный: конфиг держит путь
к ещё не существующему файлу и говорит об этом строкой, а не отказом.

```bash
mkdir -p ~/.config/agent-protocol
umask 077
cat > ~/.config/agent-protocol/secrets.env <<'EOF'
TELEGRAM_BOT_TOKEN=<токен бота>
TELEGRAM_CHAT_ID=<id чата>
EOF
chmod 600 ~/.config/agent-protocol/secrets.env
```

- Имена ключей — транспорта (`packages/transport-telegram`), не проекта; ядро
  протокола о вендоре не знает.
- Файл **вне git** и вне репозитория. В конфигах не лежат значения — только путь
  (R4/R14: репозиторий говорит ЧТО доставляется и какими словами, машина — ГДЕ лежат
  креденшлы).
- Нет файла — уведомления просто не доставляются; `init` и `doctor` об этом скажут,
  но поднимать роли ящик будет.

## 3. `init` — машинный конфиг одной командой

Сперва **план**, потом то же самое с `--write`:

```bash
# план: печатает по шагам, что запишет и что создаст
pnpm -F agent-protocol cli init \
  --instance lle-agents \
  --agent claude-code --exec "$(which claude)" \
  --operator curator \
  --secrets ~/.config/agent-protocol/secrets.env

# то же самое, но по-настоящему (в конце сам гоняет doctor)
pnpm -F agent-protocol cli init \
  --instance lle-agents \
  --agent claude-code --exec "$(which claude)" \
  --operator curator \
  --secrets ~/.config/agent-protocol/secrets.env \
  --write
```

Что делает и чего не делает:

| флаг | смысл |
|---|---|
| `--instance <id>` | КЕМ этот ящик себя называет (R13). Не угадывается: без флага — отказ, потому что догадка подняла бы роль чужой машины. Занятый соседом id — предупреждение с именем соседа |
| `--agent <kind> --exec <path>` | где на этой машине бинарь агента; резолв через PATH, а не набором пути руками |
| `--operator <role>` | кто сидит за ящиком: этим подписывается `hold`, набранный без `--by` |
| `--secrets <path>` | ГДЕ лежит файл секретов (см. §2). Файл не создаётся никогда |
| `--no-doctor` | остановиться на записи — для ящика, у которого ещё нет сети |
| `--offline` | не ходить в сеть (см. ниже) |

Результат — `~/.config/agent-protocol/local.json` (перекрывается `--local-config`):
`instance`, `operator`, `agents.<kind>.exec`, `secrets.envFile`. Ничего из политики
(права, потолки, модель, ветка, тексты уведомлений) машинный конфиг не несёт и
отвергает по имени — это репозиторий.

Чекаут почты создаётся **вместе с fetch**. Это не оптимизация: чекаут, сделанный
руками без fetch, читается как `mail: never pulled` в каждом кадре — ящик выглядит
введённым в строй и работает по вчерашней почте.

**Одно сетевое действие переживает план.** На ящике, где чекаута почты ещё нет,
чтение «занят ли этот id соседом» делает настоящий `git fetch` ветки почты
(`origin/<branch>` двигается, больше ничего) — иначе предупреждение о занятом id
пришло бы ПОСЛЕ того, как id занят. `--offline` от этого чтения отказывается и
говорит об этом строкой.

## 4. `doctor` — чек-лист готовности

`init --write` кончается им сам; отдельно — когда ящик уже стоит:

```bash
pnpm -F agent-protocol cli doctor
```

Строки, которые он даёт (✓/✗ с причиной), и как читать кресты. Их **десять** на
обычном ящике, и «десять» — не константа: пара `agent: …` печатается на КАЖДЫЙ
объявленный worker, а `mail: checkout freshness` не печатается вовсе, если чекаута
нет (проверять нечего). Сверять вывод построчно с этой таблицей — то, для чего она
здесь; незнакомая строка в выводе значит, что устарела таблица.

| строка | крест значит |
|---|---|
| `config: repository` | конфиг протокола в репозитории не читается по указанному ref |
| `config: machine` | `local.json` не парсится — имя неизвестного ключа названо |
| `config: instance` | ящик без имени при объявленных в репозитории инстансах — **он не поднимет никого**; чужой/необъявленный id — не ошибка, а «стенд: ролей этого проекта не поднимает» |
| `agent: binary (<worker>)` | бинарь не найден в PATH **дочернего процесса** (PATH демона и PATH сессии — разные вещи): спавн упал бы с уже взятой арендой. Лечится объявлением пути в машинном конфиге — `agents['<worker>'].exec`; строка называет и слой, откуда путь взят (флаг / машинный конфиг / умолчание) |
| `agent: headless run (<worker>)` | бинарь есть, а живого `-p`-прогона нет: креденшлы в домашнем каталоге протухли. Это отказ, который снаружи больше всего похож на успех — демон поднимает сессии, каждая умирает на первом вызове |
| `git: origin` | нет remote `origin`; url печатается замаскированным (токен в url не выводится — правило 10) |
| `git: fetch` | чтение из origin не проходит |
| `git: write access (dry-run push)` | ящик читает, но не пишет: сессия умрёт на ПОСЛЕДНЕМ шаге — на доставке, уже сделав работу |
| `mail: checkout` | чекаута почты нет вовсе — вопрос про ЯЩИК, а не про прогон: создать worktree **с fetch** (созданный без него читается как «никогда не тянули») |
| `mail: checkout freshness` | чекаут есть, но не годен: сидит на чужой ветке, грязный или с неотправленными коммитами. Строку выдаёт тот же судья, которым демон отказывает в запуске (`mailCheckoutVerdict`) — крест здесь и отказ демона это одна фраза, а не две похожие. Появляется только если предыдущая строка зелёная |

Команда **ходит в сеть и тратит один вызов агента** — в этом её смысл: этих фактов
нет ни в одном файле. `--offline` оставляет их незаданными и говорит об этом в
строках, но никогда не выдаёт за пройденные. `--probe-timeout <sec>` — потолок
сетевых проб.

Развилка, о которой стоит знать заранее: в организации могут быть **выключены deploy
keys политикой** — тогда право записи даётся не ключом репозитория, а аккаунтом или
machine user, и строка `git: write access` красная при полностью правильном ключе.

## 5. Демон резидентом

Юнит **генерируется с этого ящика** (репозиторий, этот интерпретатор, путь к CLI):
юнит, набранный руками на каждой машине, — первое, что протухает.

```bash
pnpm -F agent-protocol cli orchestrator systemd install            # печатает юнит и путь
pnpm -F agent-protocol cli orchestrator systemd install --write    # кладёт файл
```

Дальше — руками, и команда сама их печатает (включение юнита и linger остаются
человеческими действиями по R14):

```bash
systemctl --user daemon-reload                                  # без него systemd юнита не видит
systemctl --user enable --now lle-orchestrator.service
loginctl enable-linger "$USER"
journalctl --user -u lle-orchestrator.service -f                # тот же поток, что в логе демона
```

Имя юнита — `lle-orchestrator.service`, если не задан `--unit-name`. Набирать его
с этой страницы не нужно: `systemd install` печатает все четыре строки уже с тем
именем, которое положил, — копипастить надёжнее из вывода команды, а не отсюда.

Уровень пользовательский, не root: сессии читают машинный конфиг и креденшлы
ОПЕРАТОРА (R14).

Дальше — гейт и картинка:

```bash
pnpm -F agent-protocol cli orchestrator enable --ref origin/main --write   # без него не поднимается никто
pnpm -F agent-protocol cli orchestrator status                             # живой кадр: аренды, холды, очередь
```

`up`/`down`/`hold`/`resume`/`status` и `doctor` можно набирать без `--ref` — он берётся
из `orchestrator.ref` конфига рабочего дерева, и какой именно взят, команда печатает.
