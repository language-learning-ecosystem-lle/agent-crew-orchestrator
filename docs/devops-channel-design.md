## 1. Несущий вывод: `devops` не живёт в пользователе контура

Рамка john требует (msg-002, следствие 1): у пользователя, под которым живёт сессия `devops`,
привилегий быть не должно — ни `sudo`, ни записи в каталог глаголов, ни чтения ключа.

По факту 0.1 сессия наследует пользователя демона. **Что это значит на этом ящике — измерено из
поднятой сессии `dev-core` 2026-08-29** (значения не читались: только `id`, режимы файлов и
проверка читаемости):

| измерение | результат |
| --- | --- |
| `id` | `uid=1000(lle)`, группы: `lle`, **`sudo`**, `users` |
| `sudo -n -l` | `sudo: a password is required` — **неинтерактивная эскалация сегодня отказана** |
| `~/.ssh/github`, `~/.ssh/github-crew` (приватные ключи) | режим `600`, владелец — пользователь сессии, **читаемы ею** |
| `~/.config/agent-protocol/secrets.env` (0.7) | режим `600`, **читаем ею** |
| `~/.config/agent-protocol/instances/` | `hetzner.json` и файл второго контура — оба контура ящика |

Различие факта и вывода здесь несущее, и вот оно явно. **Факт:** сессия состоит в группе `sudo`,
и одновременно `sudo` без пароля ей отказан — то есть путь к root у неё есть, а пароля нет.
**Вывод:** держит эту дверь не протокол, а отсутствие пароля в руках сессии; ни одного объявления,
которое бы это описывало, в конфиге нет, и ни одна проверка на это не смотрит. Правило, которое
исполняется свойством окружения, а не объявлением, — ровно то, что рамка john называет
привилегией «по факту присутствия».

**Факт без вывода:** оба приватных ключа git и файл секретов транспорта читаемы пользователем
сессии. Для `devops` это уже не потенциальная дыра, а прямое нарушение следствия 3 msg-002
(«ключ агент не читает — только пользуется»).

Поднять `devops` в этом пользователе — значит выдать ему всё перечисленное по факту присутствия.
«Ходить как к удалённому» стало бы фикцией: рядом всегда лежал бы короткий путь.

Значит первая версия канала требует **второй системной идентичности**, а из 0.1–0.2 следует, что
вместе с ней — и **второго демона**: один демон поднимает все свои роли собой, разделить их по
пользователям он не умеет и уметь не должен.

Три размещения, из них выбирается одно:

| | Как | Цена | Оценка |
| --- | --- | --- | --- |
| **A** | отдельный unix-пользователь `aco-devops`, свой `systemctl --user`-демон, свой инстанс машинного конфига, свой чекаут почты | второй инстанс, вторая учётка инструмента, второй резидентный юнит | **рекомендуется**: всё это существующие механизмы (мульти-инстанс, тред 055), новых понятий ноль |
| B | тот же демон, спавн роли через `sudo -u`/`su` | демону нужна привилегия переключать пользователя — прямо против 0.8; правка `launch` в самом горячем месте контура | нет |
| C | контейнер на роль | своя сборка, свой монтаж почты, свой цикл обновления | не в первой версии |

Вариант B стоит назвать отдельно, потому что он выглядит дешёвым: он даёт демону право стать кем
угодно, то есть переносит эскалацию на компонент, который сегодня специально её не имеет.

## 2. Данные: цели и глаголы

Разрез по 0.5 — и он же ответ на «где живёт список разрешений роли».

**Репозиторий (`agent-protocol.json`, кнопка john по 0.6) — ЧТО:** какие цели существуют по имени,
какие глаголы существуют, кому какой глагол на какой цели разрешён.

```jsonc
"capabilities": {
  "targets": [
    { "id": "box-hetzner", "note": "ящик контура; для роли — обычная цель со своим адресом" }
  ],
  "verbs": [
    { "id": "service-restart", "summary": "перезапуск юнита контура", "args": ["unit"] },
    { "id": "service-status",  "summary": "состояние юнита",          "args": ["unit"] },
    { "id": "log-tail",        "summary": "хвост лога юнита",         "args": ["unit", "lines"] },
    { "id": "checkout-update", "summary": "git pull --ff-only + pnpm install в рабочей копии",
      "args": ["checkout"] },
    { "id": "disk-free",       "summary": "свободное место",          "args": [] }
  ]
}
```

и на роли — грант, то есть пересечение «цель × глаголы»:

```jsonc
{ "id": "devops", "grants": [ { "target": "box-hetzner",
  "verbs": ["service-restart", "service-status", "log-tail", "checkout-update", "disk-free"] } ] }
```

**Машина (`~/.config/agent-protocol/instances/<name>.json`) — ГДЕ:** адрес цели, порт,
пользователь на стороне цели, путь к сокету `ssh-agent`. Это расположение, оно разное на каждом
ящике и не коммитится ни на одном (0.5).

```jsonc
"targets": {
  "box-hetzner": { "host": "127.0.0.1", "port": 22, "user": "aco-verbs",
                   "agentSocket": "/run/aco-devops/ssh-agent.sock" }
}
```

Три инварианта этого разреза, каждый — отказ по имени, а не молчание:

1. **Имя глагола в репозитории ≠ реализация.** Реализация — скрипт на ящике: владелец `root`,
   режим `0755`, `/usr/local/sbin/aco-<verb>`. Соответствие «имя ↔ файл» конвенцией, и рассинхрон
   — отказ, называющий И глагол, И ожидавшийся путь;
2. **Цель, объявленная в репозитории и не описанная на машине, — отказ по имени** («цель
   `box-hetzner` объявлена, но этот ящик не говорит, где она: добавь `targets.box-hetzner` в
   машинный конфиг»). Форма не изобретается: у этого стыка уже есть прецедент — учётки, где
   «вторая половина стыка живёт на каждой машине (`accounts.<id>.configDir` машинного конфига), и
   ящик, не объявивший id, ОТКАЗЫВАЕТ запуск по имени, а не откатывается на умолчание»
   (`schema/v15-launch-account.ts:38`, `v16-instance-account.ts:39`). Цели — тот же стык буква в
   букву;
3. **Грант — единственный источник «можно».** Ни присутствие обёртки на ящике, ни доступность
   цели правом не являются: не объявлено — отказ.

## 3. Как выглядит вызов со стороны агента

Одна команда, и она — вся дверь:

```
cli devops run --target box-hetzner --verb service-restart --arg unit=agent-protocol@crew
```

Что она делает по шагам:

1. читает оба конфига и проверяет объявление: цель есть, глагол есть, грант роли покрывает пару.
   Любой из трёх отказов — по имени, с называнием того, что чинить и где (гл. 4 дисциплины);
2. подключается к цели **по объявленному каналу** — ssh под системной идентичностью канала, ключ
   в `ssh-agent`, приватная часть пользователю сессии не читается (следствие 3 msg-002). На
   стороне цели `command=` в `authorized_keys` подменяет любую переданную команду на обёртку:
   что бы агент ни отправил, выполнится глагол;
3. пишет след (гл. 5).

**Почему ssh на `127.0.0.1`, а не прямой запуск.** Это прямое исполнение рамки john: локальность
— обстоятельство размещения, а не путь доступа. Практически это даёт три вещи, которых прямой
запуск не даёт ни одной: один аудит на свою и чужую машину; невозможность привилегии «по факту
присутствия»; и **проверяемость** — тест гл. 6 существует только потому, что канал и короткий путь
физически разные вещи. Класс дрейфа «работает, потому что мы локально» мы уже оплачивали дважды
(«инструмент ответил ≠ факт», «зелёный от скипа ≠ зелёный от прохода»).

Пароль в схеме не участвует нигде: `sudo` внутри обёртки — `NOPASSWD` ровно на её путь. Условие
john «агент не узнаёт пароль» выполняется **по построению**, а не дисциплиной, — подсматривать
нечего.

## 4. Ловушка «права через PR» (§5 заготовки)

Merge PR, расширяющего возможности, = выдача прав на машине. Три следствия, и все три
исполнимы наличными средствами:

1. **Файл возможностей — документ власти.** Держим возможности внутри `agent-protocol.json` — и
   гард 4 merge-gate уже стоит без единой новой строки (0.6). Отдельный файл потребовал бы
   объявления в `powerDocuments`, то есть второго места, где это можно забыть;
2. **Применение на ящик — отдельный шаг, не автоматический из ветки.** Отдельная команда
   (`cli devops apply`), которая сверяет объявление с ящиком и печатает дифф «что появится, что
   исчезнет»; вызывается рукой john на ящике, из ветки не вызывается и в CI не стоит. Merge меняет
   ОБЪЯВЛЕНИЕ; права меняет применение;
3. **`devops` не мержит PR, расширяющие её права.** Запрет прямой и не подразумеваемый: у роли нет
   права merge вообще, а гард 4 останавливает такой PR у всех, кроме john. К этому — гард по имени
   автора: PR, трогающий `capabilities`, автором которого стоит роль `devops`, отказывается с
   называнием того, что это её собственные права.

## 5. Аудит: след в ленте

По 0.9 журнал оркестратора локален и в ленту не попадает — значит он не годится, и «привилегированные
действия живут только в системных логах» без отдельной работы никуда не денется.

След — **сообщение в тред своего контура**, потому что лента — это треды. Поля на вызов: цель,
глагол, аргументы, исход, код возврата, время. Одно сообщение на вызов — шум, который сделает тред
нечитаемым; поэтому: строка на вызов копится за ход и уходит **одним блоком в итоговом сообщении
роли**, машиночитаемым (одна строка = один вызов) и потому пригодным для сверки с системным логом
ящика.

**Отказ канала — тоже след, и он обязателен.** Отказ, которого нет в ленте, читается как «роль
ничего не делала», и это ровно та дыра, ради которой аудит заводится.

Маскирование — по гл. 7 карточки: значения не печатаются, аргументы вида `token=`/`password=`
заменяются на имя без значения.

## 6. Проверяемость — тест рамки john

Постановка требует доказательства, а не обещания. Тесты делятся на два разных по природе класса, и
разделение названо здесь честно, чтобы CI не выдавали за доказательство того, чего он не проверяет.

**Класс 1 — CI, юниты и процессные тесты пакета** (проверяют объявление и отказы):

| сценарий | ожидание |
| --- | --- |
| вызов разрешённого глагола на объявленной цели | проходит, след формируется |
| глагол не объявлен | отказ по имени глагола |
| цель не объявлена в репозитории | отказ по имени цели |
| цель объявлена, но машина не говорит, где она | отказ по имени, с называнием ключа машинного конфига |
| грант роли не покрывает пару «цель × глагол» | отказ по имени, с называнием роли и пары |
| глагол объявлен, обёртки на цели нет | отказ по имени, с называнием ожидавшегося пути |
| аргумент с секретом в следе | значение отсутствует, имя присутствует |

**Класс 2 — приёмка на ящике** (проверяет саму рамку, и в CI существовать не может: тут нужен
настроенный ящик с двумя пользователями). Место — `docs/box-setup.md` §0, тот самый пустой раздел
(0.8), чек-листом с ожидаемым отказом на каждой строке:

| под пользователем сессии `devops` | ожидание |
| --- | --- |
| `id` | в списке групп **нет `sudo`** |
| `sudo -n true` | отказ ОС |
| `systemctl --user restart <юнит контура>` напрямую | отказ ОС |
| запись в `/usr/local/sbin` | отказ ОС (`EACCES`) |
| чтение приватного ключа канала | отказ ОС |
| `ssh` к цели с произвольной командой | выполняется ГЛАГОЛ, а не команда (`command=`) |
| вызов разрешённого глагола через `cli devops run` | проходит |

Строка `id` в этой таблице стоит не для полноты. Измерение гл. 1 показало, что `sudo -n true`
отказывается **уже сегодня под `lle`** — потому что нет пароля, а не потому что нет права. Тест из
одной второй строки был бы зелёным по неверной причине: это тот же класс, что «зелёный от скипа ≠
зелёный от прохода». Проверяется отсутствие ПРАВА, и только вместе — отсутствие права и отказ
вызова.

Класс 2 — и есть доказательство, что локальность не даёт лазейки. Пока он не пройден на ящике,
канал считается непринятым, каким бы зелёным ни был класс 1.

## 8. Что уходит john через curator

1. **Гл. 1 — вторая системная идентичность и второй демон.** Это не деталь развёртывания, а условие
   исполнимости рамки, и это рука john на ящике. Вопрос по существу: заводим `aco-devops` вторым
   пользователем ящика (рекомендация A) — или john видит здесь другую форму;
2. **Гл. 2 — форма данных.** `capabilities` внутри `agent-protocol.json` (кнопка получается даром,
   0.6) против отдельного файла в `powerDocuments`. Рекомендация — внутрь конфига;
3. **Гл. 4 п. 2 — кто держит применение.** Предложено: рука john на ящике. Автоматическая
   синхронизация из ветки в первой версии не предлагается сознательно;
4. **Ключ канала** — кто его порождает и кладёт, и в каком виде живёт `ssh-agent` (юнит
   пользователя `aco-devops`). Порождение ключа — необратимое действие на ящике, то есть john;
5. **Зеркальность второго контура.** Роли две (решение 3б), обёртки на ящике общие, гранты разные. Значит
   `capabilities` второго контура описывает ТЕ ЖЕ пути обёрток — и рассинхрон двух объявлений об одном
   ящике никакой гард не поймает. Это названная дыра первой версии, а не решённый вопрос.
