## 2. Класс — и он ПЕРЕЧИСЛЕН, а не показан образцом

Класс: **судьёй доставки служит код выхода клиента, и потерянная квитанция неотличима от непришедшего письма.** В `claude-review.yml` этот приём стоит в четырёх местах, и я называю все, потому что чинить один названный случай при трёх таких же — это чинить образец:

1. **строка 658** — `if gh pr comment "$PR" --body-file "$BODY_TMP"; then delivery_mark comment ok; else delivery_mark comment failed`. Ровно эта ветвь и сработала 03.09;
2. **строка 674** — `if deliver_to_thread ...; then delivery_mark thread ok; else delivery_mark thread failed`. Здесь запись идёт через `cli new-message` (git push), и потеря ответа возможна не по HTTP, а по сети — цель перечитывается иначе (лента треда), но класс тот же;
3. **строка 764** — `if gh pr review "$PR" "$event" --body ...; then delivery_mark status ok; else delivery_mark status failed; exit 1`. Тот же `502` после записанного review покрасит джобу немедленно;
4. **строка 914** — `gh pr comment "$PR" --body-file "$BODY_TMP" || { echo "::error::..."; exit 1; }` — доставка ИТОГА доставок, тот же приём.

Из четырёх сегодня сработала одна. Три остальные — не гипотеза, а тот же код на том же канале.

## 3. Что предлагается, если «да»

**На ОТКАЗНОЙ ветви (и только на ней) перечитать цель и поискать свою запись; не найдя — метить `failed`, как сегодня.** Запись самоидентифицируема: у коммента вердикта первая строка `verdict: <слово>`, у формального статуса — автор `github-actions` и состояние в окне прогона, у письма в тред — свой файл в ленте.

Границы, которые я прошу считать частью вопроса, а не деталями реализации:

1. **успешная ветвь не трогается вовсе** — ни одного лишнего вызова там, где клиент ответил нулём. Цена правки равна нулю на нормальном такте;
2. **перечитывание не создаёт вторую запись.** Если своей записи нет — доставка объявляется несостоявшейся, повторный POST не делается: два вердикта на одной странице хуже одного потерянного круга;
3. **новой нормы не вводится.** Правка возвращает шаг к тому, что он и так объявляет («доставлено / не доставлено»), и ничего не добавляет к маршруту, правам, форме сообщения или конфигу. Класс «полевой измеренный дефект» я тут НЕ применяю и применить не могу: гард 4 всё равно ведёт PR к твоей кнопке — но разграничение называю, чтобы ты видел, чем это по существу является.

## 4. Проверяемость

- **юнит/скриптовый уровень:** ветвь перечитывания вынести в `.github/scripts/review-delivery.sh` (он уже подключается шагом) и покрыть тестом на стабе `gh`: (а) запись НАЙДЕНА после ненулевого выхода → `ok`; (б) записи НЕТ → `failed`; (в) перечитывание само отказало → `failed` НАЗВАННОЙ строкой, а не молчанием; (г) на нулевом выходе перечитывания НЕ происходит — проверяется счётчиком вызовов стаба, иначе границы 1 машинно нет;
- **живая приёмка человеком СОЗНАТЕЛЬНО не покрывается:** `502` по требованию не воспроизводится, а ждать второго случая — это ровно тот полевой критерий, который жжёт такт за тактом. Перечисление §2 строго сильнее ожидания;
- **что НЕ покрывается и почему:** сам факт, что перечитывание видит запись мгновенно после её создания (задержка репликации GitHub). Если запись ещё не видна — доставка объявится несостоявшейся, то есть поведение вырождается в сегодняшнее, и это худший случай, а не новый.
