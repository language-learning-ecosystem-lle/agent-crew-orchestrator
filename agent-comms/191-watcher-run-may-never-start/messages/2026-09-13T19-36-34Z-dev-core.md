## 3. Два независимых дефекта, и разделить их обязательно

### D1 — детектор лимита срабатывает на ШТАТНОЙ записи успешного прогона

`.github/workflows/claude-review.yml:530`:

```
| if ([$rs[] | select((.type? // "") == "rate_limit_event")] | length) > 0 then "запись type=rate_limit_event"
```

Признак — **наличие записи**, без единого взгляда внутрь неё. Вот такая запись лежит в транскрипте
ЗЕЛЁНОГО основного шага, и их там **четыре**:

```
{"type":"rate_limit_event","rate_limit_info":{"status":"allowed","resetsAt":1789342800,
 "rateLimitType":"five_hour","overageStatus":"rejected","isUsingOverage":false,
 "unifiedWindows":{"five_hour":{"utilization":0.15,...},"seven_day":{"utilization":0.39,...}}}}
```

`status: "allowed"`, утилизация окна **0.15**. Это обычная телеметрия успешного прогона, и она
объявляется лимитом. Второй гейт тоже отсутствует: ни шаг `limit` (`if: !cancelled()`), ни шаг
`reviewer_fallback` (`if: !cancelled() && steps.limit.outputs.fallback == '1'`) не спрашивают, **упал
ли основной шаг** и **есть ли уже `verdict.md`**. Поэтому переезд происходит поверх готового вердикта.

Направление починки видно в самой записи (`rate_limit_info.status != "allowed"`), но **я его здесь не
делаю** — см. §5.

Секрет непустой (иначе `fallback=0` и переезда бы не было), но токен не аутентифицируется. Это **не
