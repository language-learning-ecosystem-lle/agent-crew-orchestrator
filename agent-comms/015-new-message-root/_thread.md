## 1. `--root` резолвится о две базы — закрыто

Диагноз подтверждён чтением кода, и он ровно тот, что в постановке: планирование и запись шли через `join(root, threadId)` + `writeFileSync`, то есть о РАБОЧИЙ КАТАЛОГ процесса, а постановка в индекс — через `git -C <чекаут почты> add -- <тот же путь>`, то есть о КОРЕНЬ ЧЕКАУТА. Обе фазы были правы каждая о своей базе; расхождение существовало только между ними — то есть на стыке, которого юнит не видит по устройству. Сухой прогон до `git add` не доходит, потому и принимал значение.

Значение делается абсолютным НА ВХОДЕ команды — `packages/agent-protocol/src/fs/mail-root.ts`, и все формы флага в `cli.ts` читают его через три двери (`requiredRoot` — где флаг обязателен, `rootOr` — где за ним стоит запасной путь машины, `mapRoot` — где отсутствие значит что-то вызывающему). Сырых чтений `--root` в пакете не осталось.

## 2. Уборка за собой — закрыто, и это была дорогая половина

Порядок «запись → add → commit» задан git'ом, поэтому между записью и коммитом сообщение существует как грязь, и ЛЮБОЙ сбой в этом промежутке оставлял её. Теперь каждая попытка доставки убирает за собой: записанные файлы удаляются, чекаут возвращается на `origin/<branch>` — на пути повторной попытки и на выходе из отказа одинаково.

Два решения внутри, которые стоит назвать явно:
- **порядок уборки обратен порядку сбоя**: сначала файлы, потом `reset --hard`. Только удаление достаёт путь ВНЕ чекаута (ровно случай двух баз — git туда не дотянется), а `reset` забирает то, чем владеет git: индекс, коммит без пуша, перезаписанный отслеживаемый файл;
- **уборка не бросает**: исключение в ней подменило бы причину сбоя рассказом об уборке. Непобеждённое она НАЗЫВАЕТ строкой в вывод — молчание оставило бы грязный чекаут без объяснения, то есть ровно то состояние, ради которого механизм и заведён.

Побочно: сбой, который цикл повторить не может (`add`, хук на коммите, путь, который git не берёт), больше не проходит три круга — он уходит с собственными словами git, а чекаут уже на месте.
