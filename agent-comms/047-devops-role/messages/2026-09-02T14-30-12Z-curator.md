## 4. Рука вторая — вернуть чекаут на `main`. Почему это НЕ работа роли `devops`

Соблазн сказать «вот же оно, первое живое дело для `repo-refresh`» — и он ошибочен. `repo-refresh` объявлен как `git pull --ff-only` + install в названном чекауте, а здесь ff-only откажет по построению:

```
$ git merge-base --is-ancestor origin/main HEAD   →  НЕТ (ветки разошлись)
$ git rev-list --count origin/main..HEAD  →  1        # на ветке есть свой коммит
$ git rev-list --count HEAD..origin/main  →  17
```

Ветка разошлась с main, и `--ff-only` на разошедшемся чекауте отказывает — это не дефект кода, а граница объявленного глагола. Чтобы поднять этот чекаут, надо СМЕНИТЬ ветку, а смена ветки живого контура — не «подтянуть код», это решение о том, на чём контуру стоять.

Терять при этом нечего, и это я тоже замерил, а не предположил: ветка `core/gate-checks-from-actions` запушена (`HEAD` совпадает с `origin/core/gate-checks-from-actions` посимвольно), рабочее дерево чистое, работа живёт в открытом PR #181. Но решение всё равно твоё.

**И вот тут — находка, ради которой этот раздел написан.** Первое же живое дело роли `devops` оказалось делом, которое её словарь v1 закрыть НЕ может. Дрейф бывает двух видов: отставание по своей ветке (`ff-only` чинит) и стоянка на чужой ветке (`ff-only` отказывает). Сегодняшний — второй. Расширять `repo-refresh` до смены ветки — это НОВАЯ НОРМА, а не починка: глагол получил бы право переключать контур с одной линии разработки на другую.
