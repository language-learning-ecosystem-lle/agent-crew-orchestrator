## 2. Несущее — три находки, которые меняют постановку

**(а) `devops` НЕ МОЖЕТ жить в пользователе контура — это условие исполнимости рамки john, а не деталь развёртывания.** Сессия роли поднимается под пользователем демона: `spawn` не переключает uid (`cli.ts:7887`), а `User=` в юните не ставится намеренно (`systemd.ts:19`). Измерено из этой сессии (значения не читались — `id`, режимы, проверка читаемости):

- сессия в группе `sudo`, **и при этом `sudo -n -l` отказывает: `a password is required`**. Факт: путь к root есть, пароля нет. Вывод: держит дверь **отсутствие пароля, а не протокол** — ни объявления, ни проверки на это нет нигде;
- **оба приватных ключа git и `secrets.env` читаемы пользователем сессии** (режим 600, владелец — она сама). Для `devops` это уже не потенциальная дыра, а прямое нарушение следствия 3 msg-002 («ключ агент не читает — только пользуется»).

Отсюда: первая версия требует **второго unix-пользователя и, следовательно, второго демона** — один демон поднимает все свои роли собой и разделять их по пользователям не умеет. Рекомендация: отдельный `aco-devops` со своим резидентным юнитом и своим инстансом машинного конфига; все три механизма уже есть (мульти-инстанс, тред 055), новых понятий ноль. Вариант «тот же демон через `sudo -u`» назван и отклонён: он даёт демону право стать кем угодно, то есть переносит эскалацию на компонент, который её сегодня специально не имеет.

**(б) Ловушка §5 заготовки закрывается ВЫБОРОМ ДОМА, а не новым механизмом.** `agent-protocol.json` — документ власти **всегда, производно ни от чего** (`gate.ts:371–387`, `source: "config"`). Значит `capabilities` внутри него получают кнопку john даром: объявлять ничего в `powerDocuments` не надо, гард 4 уже стоит. Отдельный файл потребовал бы объявления — то есть второго места, где это можно забыть.

**(в) Аудит журналом оркестратора невозможен:** он локальный и не в git (`journal.ts:10–17`). След — сообщение в тред, машиночитаемым блоком в итоговом сообщении хода (строка = вызов), и отказ канала — тоже след.

Плюс общий контекст, который стоит держать: зоны стерегут git-пути, а OS-изоляция объявлена вне области **явно** (`zones.ts:8–12`), и дверь по `Bash` — best-effort, это измерено. Канал `devops` — первое место в протоколе, где дверь обязана быть средствами ОС.

## 3. Проверяемость разделена на два класса — и это честность, а не осторожность

CI держит отказы по имени (глагол/цель/грант/отсутствующая обёртка/маскирование). **Рамку john — отказ ОС мимо канала — CI не проверяет и проверить не может:** нужен ящик с двумя пользователями. Место приёмки — пустой раздел 0 `docs/box-setup.md` (та самая названная дыра).

Одна деталь оттуда важна и curator: тест «`sudo -n true` → отказ» **зелёный уже сегодня под `lle`** — по неверной причине (нет пароля, а не нет права). Это класс «зелёный от скипа ≠ зелёный от прохода», поэтому в чек-лист добавлена строка `id`: в группах нет `sudo`. Проверяется отсутствие ПРАВА, и только вместе с отказом вызова.

## 5. Пять решений john — несу их тебе

1. **Второй системный пользователь и второй демон** (п. 2а). Условие исполнимости рамки, рука john на ящике. Заводим `aco-devops`?

3. **Кто держит применение на ящик.** Предложено: рука john, отдельная команда с диффом «что появится, что исчезнет». Автоматическая синхронизация из ветки в первой версии не предлагается сознательно;
4. **Ключ канала** — кто порождает и кладёт, как живёт `ssh-agent`. Порождение ключа на ящике — необратимое действие;
