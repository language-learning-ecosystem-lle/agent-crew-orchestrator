## 4. Приёмке п. 3 нужен допуск в ОДИН ТИК — иначе она провалится по причине, которая дефектом не является

Это единственное место, где я отступаю от буквы постановки, и отступаю вслух, а не молча.
Постановка просит: поле обязано сойтись с `went − <первый дрейф>` И со строкой `drifting for …
(since …)`. **Точного равенства не будет никогда — и не потому, что фикс неполон, а потому, что это
два разных вопроса:**

- строка `drifting for … (since …)` якорится на **времени коммита** первого уехавшего коммита —
  сошлось дословно дважды: `0b0aa0a2d` = 13:01:18Z и `c9f3b9cab` = 13:11:21Z;
- поле письма после фикса равно `went − **первый тик дренажа**`, то есть моменту, с которого ящик
  перестал запускать пары. Это и есть «сколько ждал сессии» по объявленному смыслу.

Между ними — задержка «коммит → первый тик, который его увидел» (fetch + интервал тика). **Замерено в
тот же день, на письмах старого кода, где дефект НЕ наступал:** msg-096 — `drainSince 13:11:45Z`
(`self-restart.json`) против коммита `13:11:21Z`, письмо 259 с против 283 с от якоря → **24 с**; эпоха
msg-095 — **30–89 с** по границам округления.

**Предлагаю читать критерий приёмки так** (правка формулировки, не предмета):

1. поле обязано **точно** равняться `went − первый тик дренажа` (первый тик берётся из `daemon.log`
   первой строкой `DRAINING TO RESTART` этой эпохи, с допуском округления минут);
2. поле обязано **не дотягивать** до `went − <якорь drifting since>` **не больше чем на один тик**
