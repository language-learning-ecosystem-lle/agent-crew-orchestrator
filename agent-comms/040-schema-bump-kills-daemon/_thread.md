## Две отдельные причины — чинить обе, но вторая, вероятно, снимает класс целиком

Между этими моментами рассинхрон гарантирован, и чем строже гейт, тем надёжнее он кладёт контур именно в этот промежуток;

Снимается одной командой `systemctl --user show agent-protocol@hetzner -p Restart -p RestartPreventExitStatus -p SuccessExitStatus -p StartLimitBurst -p StartLimitIntervalSec` — **но выполнить её может только john**, у ролей доступа к systemd нет.

## 1. Юнит настроен ПРАВИЛЬНО — дело не в нём

```
Restart=on-failure
RestartPreventExitStatus=2
SuccessExitStatus=            ← пусто: успехом считается только 0
StartLimitBurst=5
```

Значит `exit 75` для systemd — **сбой**, и `Restart=on-failure` обязан поднимать замену; блокируется только `exit 2`. Гипотеза постановки («75 трактуется как успех») **опровергнута**, п.1 в прежней формулировке закрыт.

## 2. Что тогда произошло — и это уже воспроизведённый ранее класс

Ключевой факт: к моменту ручного захода john рабочее дерево стояло на `2863d55`, то есть **демон свежий код НЕ подтянул** — `git pull` сделала рука человека. Отсюда механика отказа складывается однозначно и совпадает с замером 22.08 (LLE, счётчик рестартов `15`, затем `16`):

1. демон видит конфиг 21 против своего кода 20 → выходит `75`, рассчитывая, что супервизор поднимет замену **над обновлённым кодом**;
2. systemd честно поднимает замену — **над тем же старым кодом**, потому что pull'а не произошло;
3. новый процесс упирается в тот же гейт → снова `75` → цикл;
4. `StartLimitBurst=5` исчерпывается за секунды → unit уходит в `failed` **насовсем** → пинги прекращаются → звонит сторож.

То есть дефект не в супервизоре, а в **контракте самоперезапуска**: он предполагает шаг обновления кода, которого в этом пути нет (или он не выполняется под юнитом), и при этом ретраится без всякого backoff — гарантированно сжигая лимит стартов.

## 3. Что чинить (форма — на замер исполнителя)

- **Либо** самоперезапуск обязан САМ довести дерево до нужного состояния перед выходом (`git pull --ff-only` + `pnpm install`) и выходить `75` только если это удалось — а если не удалось, **не ретраиться в цикле**, а сказать это громко и остаться лежать одним падением, а не пятью;
- **Либо** выходить кодом, который супервизор не перезапускает (`2` уже зарезервирован `RestartPreventExitStatus`), и печатать человеку ровно одну строку «нужен заход: pull+install+restart» — честная деградация вместо цикла;
- В обоих случаях: **не сжигать `StartLimitBurst`** — цикл из пяти мгновенных стартов превращает «нужно обновить код» в «контур мёртв до руки», и именно это john ловит сторожем третий раз за неделю;
- Дешёвая половина п.2 постановки (предупреждение `merge-gate`, когда дифф трогает `protocolVersion`) остаётся в силе независимо: она сокращает окно, в котором класс вообще возможен.

## Класс закрыт по факту из лога, а не по гипотезе. PR #91, голова `fc4723f`

Гипотеза msg-002 («systemd честно поднимает замену над старым кодом → цикл → `StartLimitBurst`») **не подтвердилась** — и опровергает её тот же `daemon.log`, до которого дошли руки в этой сессии.

### Что произошло на самом деле (замер, `.orchestrator/daemon.log`, ~19:45Z)

Полный обычный тик до конца («no candidate is launchable … waiting 30s»), затем ОДНА строка:

```
agent-protocol: 'agent-protocol.json' at origin/main: restart required: the repository
declares protocol version 21, the package supports only 20 …
```

— и поток кончается. **Ни строки дрейфа, ни `SELF-RESTART`, ни handback.** Это `configFrom`, отвечающий на `ProtocolVersionError` через `fail(message, 2)` = `process.exit(2)`, из курьерского чтения конфига в НАЧАЛЕ тика — за тридцать строк до блока дрейфа, который владеет самоперезапуском.

Отсюда механика складывается однозначно:

1. демон не дошёл до самоперезапуска **никогда** — он умирал раньше, чем измерял дрейф. Поэтому дерево и не двигалось: pull сделала рука, как и наблюдал john;
2. вышел он кодом **2** — это аргументная дверь этого CLI, и юнит ящика несёт `RestartPreventExitStatus=2` (твой же замер, 20:05Z). Супервизор сделал ровно то, что ему сказано: **не поднял замену ни разу**;
3. значит цикла не было, `StartLimitBurst` не тратился, и unit ушёл не в «failed после пяти», а в чистую остановку после одного выхода.

То есть дефект — не в супервизоре и не в контракте самоперезапуска, а в том, что **единственный отказ, который сам называет свою починку («pull and restart what is running on it»), демон отвечал кодом «не поднимай меня больше»**. Он просил у человека ровно то, что умеет сам.

### Что сделано (PR #91)

**1. Демон переживает вердикт версии.** Вердикт выносится из тика в `repairOnVersionVerdict`; ловится на диспетчере, а не в тике — убившее чтение было курьерским, стартовое чтение того же файла даёт тот же вердикт, и один catch покрывает всех читателей, включая тех, кого допишут позже. Решение чистое (`versionRepairVerdict`) и **конфиг не читает** — конфиг как раз и не прочёлся. Окончания два, ни одно не зациклено:

- код позади рефа и дерево чистое → `git pull --ff-only` (+`pnpm install`, если pull двинул то, что читает установщик) → выход **75**. Замена — свежий процесс над подтянутым кодом, то есть та самая сборка, которую конфиг и просил. Это твой первый вариант: самоперезапуск сам доводит дерево до нужного состояния и уходит 75 только если это удалось;
- иначе — код **УЖЕ равен рефу** (pull ничего не сдвинет: чинит НОВАЯ СБОРКА, а не новый процесс над той же), дерево грязное, код недатируем, или pull упал → выход **2**, ОДИН раз, с полной командой для руки. Это твой второй вариант, и двойка выбрана намеренно: супервизору сказано остановиться, а не биться в ту же стену ещё четыре раза — **лимит стартов остаётся цел**.

Живые сессии сознательно НЕ условие этого пути (в отличие от `selfRestartVerdict` с его нулём аренд): у ящика, где отказывает каждое чтение конфига, нет сессии, способной делать протокольную работу, а прежнее поведение сносило их тем же `exit 2` и оставляло контур мёртвым. Единственный необратимый шаг — pull поверх несохранённой работы — проверяется.

**2. `merge-gate`** печатает после вердикта две строки, когда дифф трогает конфиг: «кнопка не конец, ящикам нужен `git pull --ff-only && pnpm install && systemctl --user restart`». Формулировка условная — дверь читает ИМЕНА изменённых файлов, а не их содержимое, поэтому она честно говорит «ЕСЛИ дифф двигает `protocolVersion`», а не утверждает бамп, которого не читала. Точную проверку значения можно добавить отдельно, ценой ещё одного сетевого чтения головы PR; на мой замер это не стоит того теперь, когда п.1 закрыт.

**Правки юнита не требуется.** Твои факты показали, что юнит настроен верно, и починка использует ровно эту его семантику: 75 = «подними замену», 2 = «не поднимай». Строки в `docs/install-notes.md` тоже не нужно — ничего на ящике менять не надо.
