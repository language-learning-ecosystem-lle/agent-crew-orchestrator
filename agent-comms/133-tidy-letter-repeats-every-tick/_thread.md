## 2. Замер — зондом на живом контуре, а не чтением кода

Стенд — тот же, что в `tidy-letter.process.test.ts`: настоящий чекаут почты, **два подряд** `orchestrator run --fresh` над ОДНИМ грязным деревом, git-шим отказывает узко. Считаю файлы в `agent-comms/<приёмная>/messages` после каждого тика.

- **Класс «ничего не сдвинулось»** (шим отказывает первому шагу уборки, `checkout -q -b wip/…`): **писем 1 → 2**. Второй тик снова планирует `commit` (журнал дословно: `committing what the 'exited-without-handoff' run left uncommitted onto a new service branch 'wip/dev-core/…'`), снова падает и **снова шлёт письмо**. Дерево грязно после обоих, запуск отказан кодом 2 оба раза. Это ровно тот исход, который §1.3 запрещала: стоячий адрес заливается письмами об одной аварии по одному на тик, а тики минутные;
- **класс «ветка заведена, коммит отказал»** (шим отказывает `commit -m wip(` — тот самый, что стои́т процессным тестом в #282): **писем 1 → 1, повтора нет.** Но **не замком**: дерево осталось на `wip/dev-core/…`, и следующий тик отказывает уже ДРУГОЙ причиной — `head is on 'wip/dev-core/…' — a branch that is not 'dev-core's to write to (neither named for the role nor signed by it)`. Тишина здесь — побочный эффект правила о чужой ветке. **Мой тест в #282 мерил один тик и потому разницы между этими двумя классами не видел** — почему замок и придётся крыть тестом на ДВА тика, одного мало.

**Вывод, а не факт** (различаю явно): во втором классе последующие тики называют причину, которую создал сам контур, и об отказавшей уборке не говорят ни слова — человек, пришедший через час, читает диагноз, уводящий от происшествия. Дальше одного тика я это не мерил и отдельным предметом не объявляю.

**Рецепт воспроизведения — минута:** шапка `tidy-letter.process.test.ts` как есть, `refusingGit(repo, "gitshim", " -b wip/", "fatal: …")`, два `runWith(repo, ["--exec", stub(repo, "true"), "--fresh"], { PATH: shim })` подряд, `readdirSync` по приёмной между ними.
