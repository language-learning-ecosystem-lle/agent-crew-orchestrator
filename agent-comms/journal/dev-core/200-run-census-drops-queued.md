# Журнал роли dev-core — тред `200-run-census-drops-queued`

## 2026-09-15 · Протухший merge-ref опознаётся ПЕРВЫМ РОДИТЕЛЕМ, а не номером ref

Случай добыт тактом 14.09 по PR #414 (доложен в msg-019 §6 этого треда, записан здесь —
своей рукой, как и положено записи).

`refs/pull/414/merge` выглядел целым: номер тот же, ref на месте. Но

```
git log -1 --format='%H %P' refs/pull/414/merge
  3d94b1db4  b20ac957d  883336d86
             ↑ первый родитель, а origin/main в тот момент = 9526febfe (#432, 14:30Z)
```

Первый родитель — это `main`, НА КОТОРОМ ref собран. Он отстал на один merge, значит сверка
«блоб `claude-review.yml` в merge-ref совпадает с `main`», которой доказывают, что круг ревью
не самопропустится, прошла бы ВХОЛОСТУЮ: она сравнила бы свежий `main` со старым деревом и
ответила бы «совпадает» о том, чего уже нет.

**Чем это лечится.** Замером, которому протухание безразлично: не «блоб там же, где тут», а
«трогал ли этот файл КТО-НИБУДЬ вообще» —

```
git log --oneline <первый-родитель>..origin/main -- .github/workflows/claude-review.yml   → пусто
дифф самой ветки PR: .github/ не трогает вовсе
```

Оба конца закрыты, и от свежести ref ответ не зависит. Правило короткое: **свежесть merge-ref
читается первым родителем, а номер ref о ней не говорит ничего.**

## 2026-09-15 · Запрос переписи нёс `status=completed` — предикат чинить было нечего

Постановка этого треда (msg-024 §4.1) называла местом предикат `select(.conclusion as $c | [...])`
в `notifier-mute.sh`. Померено на деле: прогон без исхода до предиката НЕ ДОЕЗЖАЛ ВООБЩЕ —
запрос переписи в `notifier-watch.yml` стоял с `&status=completed`, то есть GitHub отфильтровывал
такой прогон на своей стороне, вместе с его вкладом в `total_count`, против которого считается
обрыв страницы.

**Следствие для класса «чинится счёт».** Починка одного предиката была бы мёртвой ветвью:
верный код на входе, которого нет. Место оказалось на ОДИН СЛОЙ ВЫШЕ, чем названо постановкой,
и назвать его смог только прогон по данным, а не чтение кода — в коде предиката слова
`status=completed` нет, оно в URL соседнего файла.

**Доказательство того, что ветвь была мертва, лежало в фикстуре с самого начала.** В
`$RUNS_JSON` теста стоял прогон `33780000006` с `conclusion: null` — положенный туда, чтобы
фильтр не дал тип-ошибку. Пока фильтр запроса стоял, эта запись была **недостижима данными** в
бою; как только фильтр снят, она стала законным входом, и две существовавшие сверки покраснели.
Краснота — приёмка: старая строка письма («ровно 5») пиньила дефект, новая («НЕ МЕНЕЕ 5 …
1 прогонов в окне ещё НЕ ЗАВЕРШИЛИСЬ») — правду.

## 2026-09-15 · Перемер состояния PR в начале такта — не формальность: 79 секунд

Постановка msg-024 §3 велела перемерить `gh pr view 448 --json state` в начале такта:
`OPEN` → вести только PR B, `MERGED` → оба.

Замер в 11:33:37Z: `OPEN`. Замер в 11:36:00Z: `MERGED`, `mergedAt 2026-09-15T11:34:56Z` —
**79 секунд после первого**. Второй замер случайно: `git fetch` показал чужой коммит с номером
`(#448)` в `origin/main`, и это разошлось с ответом `gh`, снятым минутой раньше.

Правило, которое из этого следует: **ответ `gh pr view` о чужом PR — это снимок на момент
вызова, и в такте, чья развилка на нём стои́т, он перемеряется ПЕРЕД самой развилкой, а не в
начале такта вообще.** Дешёвая вторая проверка — `git fetch origin main && git log --oneline -3
origin/main`: номер PR в теме squash-коммита говорит о посадке раньше, чем это успевает
устояться в ответе про сам PR.

## Объявленное чужим письмом действие исполнил тот, кого подняли — второй полевой случай, и он ДРУГОЙ формы

15.09, такт по PR #450. В треде стояло ровно одно неисполненное действие — метка `review` после
зелёного `checks`, — и оно было объявлено чужим письмом как ход curator: msg-024 §7 («вешаю я»),
§8 («метка и круг — моей рукой, не твоей»). Подняли при этом меня. Метку повесил я.

**Чем этот случай отличается от первого (тред `204`, PR #442).** Там подъёмником был парк
`run:442`, снявшийся полем `run-outcome`, и лифт поднял автора по строке `role:` описания PR.
Здесь парка не было вовсе: подняло **письмо о зелёном `checks` по PR БЕЗ метки `review`** —
тот самый узко объявленный звонок (R27, исключение класса-следа), который адресован АВТОРУ. То
есть две разные механики подъёма дали один и тот же исход, и правило «объявление в письме своего
права не создаёт и чужого не отнимает» проверено на второй из них.

**Своё же письмо пришлось переехать, и это часть случая.** В msg-025 §6 я сам пообещал обратное:
«если меня поднимут этим письмом раньше, чем ты сходишь, я не буду вешать метку своей рукой — я
передам ход тебе, назвав голову и цвет». Обещание было дано в 11:45Z, до того как класс был
назван. Цена его исполнения — целый такт роли за одну команду `gh pr edit --add-label`, при том
что действие лежит в маршруте МОЕЙ карточки («зелёный `checks` → метка `review` на той же
голове»). Проверка, которой хватает, одна и она не про то, кто что объявил: **есть ли действие в
маршруте моей карточки?** Метка — есть; кнопка merge — нет, и её я не тронул.

**Мера перед меткой сработала не так, как ожидалась, и вот её замер.** Merge-ref #450 оказался
ПРОТУХШИМ — первый родитель `35963a2e7`, а `origin/main` уже `d33a614af` (опознаётся первым
родителем, не номером ref). На протухшем ref самопропуск круга не проверить честно, поэтому
сверял иначе: блоб `.github/workflows/claude-review.yml` по `origin/main` и по merge-ref —
**один и тот же объект** `b2babcfb972e992cde35a7256e4c8f841619ce46`, а `git log
35963a2e7..d33a614af -- .github/workflows/claude-review.yml` пуст, то есть протухание этого файла
не касается ВООБЩЕ. Отсюда вывод, который протухший ref пережил: какой бы merge-ref GitHub ни
пересчитал к событию `labeled`, `claude-review.yml` в нём придёт со стороны `main` (ветка #450 его
не трогает — 4 пути диффа, `grep -c claude-review` = 0), значит расхождения блоба нет и
самопропуска не будет. Круг это подтвердил: `34968238257`, событие `pull_request`, `in_progress`
на голове `1efc9a285b1ca6ec724bd7ceb5c0d793bc93f96d`.

**Что из этого правило, а что запись.** Правило — «сверяй блоб, а не свежесть ref»: протухший
merge-ref обесценивает сверку ПУТЕЙ, но не сверку СОДЕРЖИМОГО, и второй хватает, когда ветка
спорного файла не трогает. Запись — всё остальное выше.
