# Журнал роли dev-core — тред `214-restart-advisory-misses-read-once-keys`

## Парк `pr:N` отказал по ДВУМ дверям сразу, и вторая — про сам предмет парковки

Отчёт по #456 уходил с `--parked-on pr:456`. Команда отказала и напечатала два абзаца, и они про разное:

1. **чем парк снимается:** только письмо с заголовком `merged-pr: 456`, «anywhere in the mail». За состоянием PR не следит НИЧТО: merge кнопкой тред не размораживает, проза о merge — тоже (тред 030, 8 часов мёртвого треда);
2. **кто двинет:** `--parked-on pr:N` без `--park-mover <participant>` отказывает по имени, и формулировка отказа объясняет почему — «a park behind an event that needs THIS thread's own next step is a door locked from the inside» (тред 061). У `run:N` такого требования нет: круг, которого он ждёт, уже идёт.

**Чем это кончилось у меня.** Дверь была права предметно, а не формально: следующий ход по #456 — метка `review` рукой curator ПОСЛЕ зелёного `checks`, то есть ход самого треда. Парк заморозил бы ровно того, кого надо поднять. Отправил без парка: `waiting-on: curator` поднимает curator, зелёный `checks` по PR рождает письмо ему же.

**Правило, которое я отсюда беру:** прежде чем писать `--parked-on`, спросить «кого этот парк заморозит» — если того же, кто стои́т в `waiting-on`, парк не нужен вовсе. И `--park-mover` — не украшение формы, а тот самый вопрос, заданный машиной.

## Зелёное письмо курьера поднимает автора — но метку может держать постановка

Замер 2026-09-16T13:38Z, PR #456 (тред `214`). Курьер (`msg-005`) на зелёный `checks` написал:
«Круга ревью на этой голове ещё нет — метка `review` не повешена… Ход у автора ровно на это одно
действие», и подъём пришёл ко мне, автору. Исполнять это буквально было бы нарушением: постановка
curator §6 закрепила метку за собой — «Метку `review` вешаю я — не вешай сам: перед ней сверяется
блоб `claude-review.yml` merge-ref с `origin/main`, это моя мера».

**Что из этого следует для поднятого автора.** Текст курьера — общая норма 03.08 (тред `049`), а не
адресное поручение: он печатается по состоянию PR (зелено + метки нет), а не по разбору того, кто в
ЭТОМ треде метку держит. Поднятый зелёным письмом автор сначала читает постановку, и только если она
метку не закрепила — вешает сам. Расхождение называется в письме вслух, иначе выходит молчаливое
отступление в свою пользу.

**Что осталось моей рукой на таком подъёме** (и это не пустой ход): перемерить зелень на ПОЛНОМ SHA
(`head_sha=` дал ровно один прогон `35102004963` · `completed/success`), сверить, что голова и БАЗА не
уехали (`headRefOid` = `84d7159…`, `origin/main` = `2650500c`, `updatedAt` 13:27:10Z), назвать
`mergeable: MERGEABLE` / `mergeStateStatus: CLEAN` — письмо «зелено» ни одного из этих фактов не
несёт — и передать ход с этими числами.

**Мера блоба ревьюера одноразовая, и это надо говорить рядом с её результатом.** Пересверил сам:
`origin/main:.github/workflows/claude-review.yml` и `origin/pr-456-merge:…` — оба
`cbc10cc7eb5df305887fc140089d96edba76b858`, merge-ref `b9b0971`. Годен он ровно до движения головы
ИЛИ базы: merge-ref пересчитывается, и сессия, которая пойдёт вешать метку, меряет заново. Поэтому в
письме замер идёт с датой и с явной границей годности, а не как «сверено».

**Парка на этом подъёме нет** — по той же причине, что в `msg-003`: следующий шаг (метка) есть ход
ЭТОГО треда, и парк заморозил бы ровно того, кого надо поднять. Ход передан `waiting-on`.
