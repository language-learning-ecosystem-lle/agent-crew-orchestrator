# Журнал роли dev-core — тред `219-restart-calls-pnpm-by-name`

## Резолюция пути инструмента не запускает скрипт: второй отказ той же цепочки (тред 219, 17.09)

**Что произошло.** 17.09 12:23Z `orchestrator restart --pull` уложил контур на две минуты
строкой `pnpm install FAILED (code ?)`. Починка (#462) сделала две вещи: искать `pnpm`/`git`
рядом со своим `node` и разъять `FAILED (code ?)` на «процесс не стартовал» / «процесс вернул
код». Она смёржена 13:00Z, и в 15:49Z john повторил тот же жест из окружения без nvm. Обе
половины сработали — и контур лёг снова:

```
restart — pnpm install …, running '/home/lle/.nvm/…/bin/pnpm' (beside this node binary)
pnpm install FAILED — '<полный путь>' ran and exited 127: /usr/bin/env: 'node': No such file or directory
```

**Диагноз, который стоит запомнить.** `pnpm` в раскладке nvm — не бинарь, а СКРИПТ с первой
строкой `#!/usr/bin/env node`. Резолюция решает, какой файл откроет ядро; она не решает ничего
о том, найдётся ли интерпретатор — его ищет `env` ПО ИМЕНИ в `PATH` **порождённого** процесса.
То есть правильная посылка «не спрашивай `PATH` вызывающего про АДРЕС инструмента» и посылка
«ребёнку нужен `PATH`, в котором есть твой node» — разные, и первая не покрывает вторую.
Класс проверяется одной командой: `head -1 $(command -v <инструмент>)`. В этом пакете под него
попадает только `pnpm` (четыре точки спавна); `git`/`gh`/`du`/`id`/`ssh`/`ssh-keygen` и бинарь
сессии `claude` — ELF'ы, `corepack`/`npm`/`npx` не спавнятся вовсе.

**Цена диагностики без этой строки.** `exit 127` от шелла означает «команда не найдена», и
читатель, которому строкой выше напечатали полный путь до инструмента, идёт проверять именно
этот путь — уже верный. Отсюда правило отказа: `127`, чья причина — ненайденный ИНТЕРПРЕТАТОР,
обязан называть его имя и отправлять чинить `PATH` порождённого процесса. Разбирается по тексту
жалобы самого инструмента, и форм две: `env: 'node': …` (GNU) и `env: node: …` (busybox).

**Полевая приёмка ловит то, чего не ловит merge.** Обе половины #462 были смёржены, зелены и
предъявлены вердиктом ревьюера — и всё равно контур лёг, потому что приёмка П-4 (срабатывание
в поле) не наступала. Это ровно тот случай, ради которого приёмка объявлена срабатыванием, а
не кнопкой: «смёржено» и «работает» разошлись на один шаг цепочки.

**Стенд: проба обязана читать `/proc/self/environ`.** Процессный тест ставит шим `pnpm`
настоящим node-скриптом и записывает `PATH`, с которым его спавнили. Первая версия читала
`process.env.PATH` и получила каталог, который стенд подставил САМ: преload
(`NODE_OPTIONS --import`, приём треда 221 для подмены `process.execPath`) доезжает и до шима,
раз тот — node-скрипт, и переписывает `process.env.PATH` до первой строки пробы.
`/proc/self/environ` несёт исходный envp и подменой не задевается. Тем же преloadом заявляется
и сама среда `sudo -i` — «у процесса нет node в `PATH`» — изнутри процесса: снаружи так не
выйдет, потому что шелл, стартующий `tsx`, сам ищет node по `PATH`. Мутация (снятие
`env: toolEnv()` с шага) красит тест — предъявлена.
