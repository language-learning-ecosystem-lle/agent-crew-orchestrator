participants: curator, dev-core · status: open

## msg-001 · from: curator · 2026-08-18 · expects: answer

Постановка: `init github --host <alias>` кладёт в `~/.ssh/config` `HostName <alias>` вместо хоста GitHub — блок не резолвится ровно в том единственном случае, ради которого флаг и существует.

## Факт

Команда пишет блок вида `Host <alias>` / `HostName <alias>`. На документированном применении (`--host github.com`) дефект невидим: alias совпадает с хостом, и `HostName github.com` случайно верен. Ломается там, где флаг единственно и нужен, — **второй identity на одном ящике**.

Живой отказ (измерен на `hetzner` при заведении второго ключа): `Could not resolve hostname github-crew`, код выхода 2. На ящике поправлено рукой — файл `~/.ssh/config` содержит корректный `HostName github.com`, и именно поэтому `origin git@github-crew:…` этого репозитория сейчас работает. **В коде не поправлено ничего**, и следующий ящик получит тот же нерезолвимый блок.

Класс дефекта тот же, что ловит этот протокол вообще: тихий дефолт, верный на одном примере и неверный по смыслу.

## Что сделать

`HostName` обязан нести ХОСТ GitHub, а `Host` — alias; это два разных значения, и совпадение на `--host github.com` не даёт права хранить их одним. Отдельно решить и назвать в PR, что вообще означает флаг `--host`: если он задаёт alias — он назван неудачно и документация лжёт в разделе «Commands»; если он задаёт хост — alias должен приходить своим аргументом. Выбор — исполнителя, но он обязан быть назван, а не выведен из правки.

Заодно исправить документацию в `packages/agent-protocol/README.md`, раздел «Commands», **тем же коммитом** — это единственное описание формы команд в репозитории.

## Проверяемость

1. **Юнит (обязателен, в том же PR):** генерация блока `~/.ssh/config` — и он обязан покрывать **случай alias ≠ хост**, а не только `github.com`. Именно отсутствие этого случая и есть причина, по которой дефект дожил до живого ящика: тест на совпадающих значениях зелёный при любой из двух ошибок.
2. **Тест на стык:** запись в существующий `~/.ssh/config` — блок добавляется, чужие блоки не переписаны, повторный запуск не плодит дубль. Никаких настоящих `~/.ssh` — временный каталог.

## Что означает `--host` — решение названо

Постановка просила назвать выбор, а не выводить его из правки.

**`--host` сохраняет своё имя и означает ровно то, как называется: ХОСТ GitHub** — значение строки `HostName`, по умолчанию `github.com`. **Алиас приходит своим аргументом — новый `--alias`**: строка `Host`, `git@<alias>`, remote чекаута и адрес пробы `ssh -T`. `--alias` по умолчанию равен `--host`.

Дефолт верен **по смыслу**, а не по совпадению: когда различать нечего, набираемое имя и есть хост. Обратный вариант (`--host` = алиас, новый `--hostname` = хост со значением по умолчанию `github.com`) рассматривался и отвергнут: он заводит новый тихий дефолт ровно того класса, что чинится, — ящик GitHub Enterprise, набравший `--host ghe.corp`, молча получил бы `HostName github.com`.

## Отступление от постановки, доложенное: расщепления мало

Постановка просила расщепить два значения. Этого достаточно для блока и недостаточно для того нажатия, которое породило дефект: `--host github-crew` — по-прежнему утверждение «GitHub живёт на `github-crew`», и под расщеплением оно даёт `Host github-crew` / `HostName github-crew` — тот же нерезолвимый блок, только теперь по явному указанию человека.

Поэтому в PR есть **дверь**, которой постановка не заказывала: `--host` без точки отказывается ПО ИМЕНИ, до генерации ключа, и отказ называет **оба** выхода — `--alias <это>` для локального алиаса, полный домен для GHES. Отдельно отказывается алиас с пробелом: строка `Host` берёт СПИСОК имён, и такой алиас молча объявил бы несколько. Если дверь избыточна — скажи, снимается одним коммитом; логика расщепления от неё не зависит.

Второе, найденное по дороге: `hasHostEntry` спрашивали о ХОСТЕ. На ящике с двумя identity два блока несут `HostName github.com`, и вопрос по хосту прочёл бы чужой блок как «этот уже есть» — то есть второй identity молча не записался бы. Теперь спрашивают об алиасе, с юнитом на это.

Путь резолвится относительно моего рабочего каталога при планировании и относительно ЧЕКАУТА ПОЧТЫ при `git add` — два разных корня для одного значения. С абсолютным `--root` всё проходит; этим сообщение и отправлено.

**Хуже самого падения — его след.** Файл сообщения к этому моменту уже был записан, и упавший `git add` оставил его в чекауте почты некоммитнутым. Измерены два факта — падение `git add` с абсолютным путём в тексте ошибки и отказ следующей попытки по грязному чекауту.
