**6, `packages/agent-protocol/src/roles/schema.ts:587-591`.** `launchAgentSchema` получает второй
член `z.strictObject({ kind: z.literal("codex"), model: ... })` — это расширение формы: значение
`launch.agent.kind: "codex"`, которое ДО этого PR отказывала схема, теперь принимается. Это ровно
класс инцидента, из-за которого написан `schema/shape.ts` (`thread 023`, комментарий в
`schema/version.ts:33-36`: «a field added at an unchanged number is met by an older build as
`Unrecognized key` instead of "restart required"», два живых сеанса погибли на голове до бампа).
Старый бинарь (собранный до этого PR, тот же `protocolVersion: 18`) при встрече роли с
`kind: "codex"` в `agent-protocol.json` откажет строгим объектом с «Unrecognized key»/невалидным
дискриминатором, а не читаемым «требуется рестарт», потому что номер не изменился и ahead-gate не
сработает. `CURRENT_PROTOCOL_VERSION` (`schema/version.ts:38`) в диффе не тронут, шаг миграции не
добавлен, обсуждения бампа в треде `026` нет (проверил тред целиком). Диагностировал вслепую не по
докладу: `pnpm exec vitest run src/schema/shape.test.ts` зелёный (4/4) — но это ложное спокойствие,
а не подтверждение совместимости: `configShapeKeys()` (`schema/shape.ts:40-67`) считает МНОЖЕСТВО
ПУТЕЙ ключей по JSON-Schema проекции, а не множество допустимых значений дискриминатора; `kind` и
`model` как имена путей (`roles[].launch.agent.kind`, `roles[].launch.agent.model`) уже стоят в
таблице с версии 14 (со стороны `claude-code`), поэтому появление ВТОРОГО члена унии с теми же
именами полей не меняет список путей и гард молчит — это отдельный, отличный от заявленного PR
класс «дверь молчит» (критерий 11) в самом guard'е, но к диффу #74 это не снимает требования
бампа. Действие: либо бампнуть `protocolVersion` до 19 с шагом миграции (шаг может не двигать
данные, раз старые конфиги валидны и без него — норма `PROTOCOL.md:52`), либо явно принести в тред
решение curator/john о том, что это исключение и почему.
