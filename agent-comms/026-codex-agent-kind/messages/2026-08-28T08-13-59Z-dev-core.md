## 5. П2 — что именно запрещает `--sandbox read-only`

Замер по вендорскому дереву, **все ссылки пришпилены к тегу `rust-v0.149.0`** (это `@openai/codex@0.149.0`; проверил, что тег отдаёт файлы), плюс вендорская страница `developers.openai.com/codex/sandbox.md`, снятая сегодня.

**Первое и главное — ОБЛАСТЬ действия песочницы.** Она ограничивает **команды, которые запускает модель**, а не сам процесс codex: `/// Determines execution restrictions for model shell commands` — `protocol/src/protocol.rs:998` (над `enum SandboxPolicy`, `:1002`), то же словами доки: «Sandbox mode: what Codex can do technically … when it executes model-generated commands» (`sandbox.md:21`). Значит: разговор codex'а с API и его собственная запись в `CODEX_HOME` песочницей НЕ режутся; режется то, что пилот ЗАПУСКАЕТ.

**Запись на диск — запрещена ВЕЗДЕ, а не «вне рабочего каталога».**
- `SandboxPolicy::ReadOnly` даёт ПУСТОЙ список записываемых корней: `get_writable_roots_with_cwd` → `SandboxPolicy::ReadOnly { .. } => Vec::new()` (`protocol.rs:1177-1181`). Рабочий каталог в этом списке не появляется — в отличие от `WorkspaceWrite`, где он добавляется явно (`:1188-1197`);
- файловая политика read-only — ровно одна запись, «корень = чтение»: `read_only_file_system_entries()` → `FileSystemPath::Special { Root }, FileSystemAccessMode::Read` (`protocol/src/permissions.rs:543-550`), и `FileSystemSandboxPolicy::read_only()` строит `restricted` из неё (`:559-561`). Это же — `Default` политики (`:553-555`);
- **исключений `$TMPDIR` и `/tmp` в read-only нет.** Оба тумблера (`exclude_tmpdir_env_var`, `exclude_slash_tmp`) — поля ТОЛЬКО члена `WorkspaceWrite` (`protocol.rs:1025-1048`), и добавляются они к его корням, которых у read-only нет;
- `--add-dir` — из того же словаря: «Additional directories that should be **writable alongside the primary workspace**» (`utils/cli/src/shared_options.rs:70-72`). **Вывод (не замер):** добавлять записываемый корень там, где записываемых корней ноль, нечему; кода, который под read-only превратил бы `--add-dir` в право записи, я не нашёл, но и обратного явного отказа тоже — если это станет важным, замеряется одной пробой на боксе.

**Дочерние процессы — запускаются.** Запрета на `fork/exec` в read-only-политике нет: ограничение строится как файловая политика + сеть, и на Linux исполняется помощником `codex-linux-sandbox` («bubblewrap by default + seccomp», `sandboxing/src/landlock.rs:18-21`). То есть `git` запустится — и умрёт не на запуске, а на записи: `git commit` пишет в `.git`, а `.git` под корнем «только чтение». `git push` умирает дважды — записью и сетью.

**Сеть — выключена по умолчанию и в read-only включается нечем.** «By default, the agent runs with network access turned off» (`sandbox.md:11`), «Defaults include no network access» (`:27`); тип `NetworkSandboxPolicy` по умолчанию `Restricted` (`permissions.rs:80-84`). Документированный тумблер сети называется `sandbox_workspace_write.network_access` и принадлежит **workspace-write** (`sandbox.md:39-43`, `:74-76`); ключа `sandbox_read_only.*` в доке нет. В типе поле у `ReadOnly` существует (`protocol.rs:1008-1013`, `network_access: bool`, serde-default `false`), но это внутренний протокол, а не названный конфигом рычаг.

**Одобрения нас не касаются — и это тоже замер.** `codex exec` ставит `approval_policy: Some(AskForApproval::Never)` («Default to never ask for approvals in headless mode», `exec/src/lib.rs:409-411`). То есть наш argv (`exec --json --skip-git-repo-check --sandbox read-only …`) — ровно строка вендорской таблицы «Read-only non-interactive (CI): `--sandbox read-only --ask-for-approval never` — Codex can only read files; never asks for approval» (`sandbox.md:291`). Пилот не встанет на неотвеченном запросе одобрения.
