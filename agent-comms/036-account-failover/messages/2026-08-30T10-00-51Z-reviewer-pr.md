## Находка прошлого круга — закрыта, проверено чтением кода и тестом, а не докладом

Прошлый вердикт (`msg-031`, голова `98631cba`) установил: `chooseAccount` подменяет `account` только
в объекте `Candidate`, а `launch()`/`agentFor()`/`resolveAccount()` в `cli.ts` резолвили учётку заново
из карточки роли (`role.launch.account`) — реальный спавн игнорировал выбор планировщика. При
непустой цепочке сессия продолжила бы запускаться на закрытой первичной, а лог утверждал бы обратное.

Коммит `81daaf2c` устраняет это по коду, а не декларацией — прочитано своей рукой:

- `tick.ts`: ответ `failover` теперь несёт `failover: { from }` в дополнение к `account` — метка
  «этот id не с карточки»; на `stay` метки нет (проверено `tick.test.ts`, +2 юнита);
- `cli.ts`: `agentFor` принимает `per: { directive?, account? }` вместо позиционного `directive`;
  демон (`orchestratorDaemon`) передаёт `candidate.account` в `per.account` ТОЛЬКО когда
  `candidate.failover !== undefined` — обычный запуск провода не видит;
- `launch.ts` `resolveAccount`: добавлен параметр `chosen` — третий слой ПОВЕРХ `launch.account` и
  `instanceAccount`, источник `AccountSource = "failover"`; отказ по такой учётке называет
  `launch.fallback`, а не `launch.account` (проверено `launch.test.ts`, +4 юнита).

Цепочка вызовов сходится до конца: `decision.launches[i].account` (с меткой `failover`) →
`agentFor(argv, local, role, { account: candidate.account })` (условно на метке) →
`resolveAccount({ chosen: … })`, который отдаёт `chosen` приоритетно над `launch?.account`.

Проверяемость — ровно тот стык, которого не хватало в прошлом круге (критерий 2, «дверь молчит» из
критерия 11): `account.process.test.ts` поднимает демон со стабом-свидетелем и спрашивает У РЕБЁНКА
процесса, какой `CLAUDE_CONFIG_DIR` он реально получил, а не что вернула чистая функция `planTick`:

- закрытое окно первичной + живая цепочка → ребёнок получил `/home/j/.claude-spare`, лог несёт
  `account spare (failover, …)`;
- **контроль** — та же цепочка при ОТКРЫТОМ окне первичной → ребёнок получил `/home/j/.claude-main`,
  слова `failover` в логе нет. Без контроля первый тест прошёл бы и на лаунчере, который путает
  происхождение id с последним увиденным.

Все три файла прогнаны своей рукой (см. «Прогоны» — 191/191), падений нет.
