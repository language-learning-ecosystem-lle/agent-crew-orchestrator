## Находка (критерии 2, 9)

**`packages/agent-protocol/src/cli.ts` — выбранная `chooseAccount` учётка не доезжает до реально
запускаемой сессии; PR заявляет обратное.**

Тело PR и `docs/protocol-reference.md:1695-1697` утверждают: «кандидат едет дальше с ПОДМЕНЁННЫМ
полем `account`, поэтому ни `shelvesAgainst`, ни дверь авторизации, ни лаунчер, ни журнал не знают,
что случилось переключение: **все они читают одно поле**». Это неверно для лаунчера — проверено
чтением кода, а не по докладу:

- `tick.ts:416-417` строит `chosen = choice.kind === "failover" ? { ...candidate, account: choice.account } : candidate` и кладёт его в `eligible` (→ `decision.launches`) — учётка подменена ТОЛЬКО в объекте `Candidate`, который возвращает `planTick`;
- `cli.ts:10419` и `cli.ts:10451`: `const planned = decision.launches; … for (const candidate of plan) launch(candidate, events);` — этот `candidate` (с подменённым `account`) передаётся в `launch`;
- `cli.ts:9913-9918`: `launch = (candidate, events) => { const role = registry.get(candidate.role); const profile = role?.launch; … }` — роль читается ЗАНОВО из реестра (статичная карточка), `candidate.account` нигде дальше по телу функции не упоминается — `grep -n 'candidate\.account' cli.ts` даёт пусто;
- `cli.ts:9944-9949`: `const agent = agentFor(argv, local, role, …)` — вызов НЕ принимает `candidate` вовсе, только `role` (статичный) и directive;
- `cli.ts:4814-4823` (внутри `agentFor`): `const account = resolveAccount({ launch: role.launch, local: local.config, instanceAccount, worker })` — читает `role.launch.account`, то есть ПЕРВИЧНУЮ учётку роли с карточки, а не выбор `chooseAccount`;
- `launch.ts:498-520` (`resolveAccount`): сигнатура не несёт параметра для динамически выбранной учётки — только `launch?.account` и `instanceAccount`.

Итог цепочки: `chooseAccount` может решить `failover` и напечатать громкую строку
(`describeFailover`: «dev-core is raised on lle-second — lle-main is quota-paused until…»), но
РЕАЛЬНО запускаемая сессия по-прежнему резолвит учётку через `agentFor`/`resolveAccount` со
статичной карточки роли (`role.launch.account`) — то есть на ТОЙ ЖЕ, только что объявленной закрытой,
учётке. Это не «лаунчер узнаёт из одного поля» (как заявлено), а «лаунчер не узнаёт вовсе»: сессия
либо упадёт на границе аутентификации/квоты той же закрытой учётки, либо (если полка уже
переоткрылась к моменту запуска) тихо спишет квоту НЕ ТОЙ учётки, про которую только что была
написана громкая строка «is raised on …». И то и другое хуже тишины, которую поле было призвано
убрать (msg-002 §4, msg-018 §6 п.3 постановки в треде): дайджест/лог теперь несёт УТВЕРЖДЕНИЕ, не
соответствующее факту.

**Почему это не поймали тесты (критерий 2 — «ждём ровно то, что проверяем»).** Восемь новых тестов
`tick.test.ts` (раздел «Проверяемость» тела PR: «учётка реально доехала до `launches`, а не только до
решения») проверяют РОВНО `decision.launches[i].account` — то есть выход чистой функции `planTick`.
Это стык `planTick`↔`chooseAccount`, а не стык `planTick`↔фактический запуск. Слой между
«`decision.launches` содержит правильный `account`» и «спавнится процесс с правильным
`CLAUDE_CONFIG_DIR`» (`cli.ts`, `launch`/`agentFor`/`resolveAccount`) не покрыт НИ ЮНИТОМ, НИ
процессным тестом — ни в этом PR, ни где-либо ещё в репозитории (`grep -n 'candidate\.account'
packages/agent-protocol/src/cli.ts` → пусто; `grep -rn 'fallback\|failover'
packages/agent-protocol/src/orchestrator/launch.test.ts` → пусто, кроме несвязанного текста «the
package defaults are the fallback»). Ровно класс, который REVIEWER.md называет «дверь молчит» —
здесь дверь не молчит, она объявляет успех, которого не было, и это тот же корень.

Сегодня в проде дефект СПЯЩИЙ: все цепочки пусты (решение john, msg-007 §2), `choice.kind ===
"failover"` не наступает ни для одной роли, `chosen === candidate` всегда, расхождения нет. Но это
латентная мина ровно под тем событием, ради которого весь тред 036 существует: в момент, когда у
какой-то роли появится непустая `fallback` и её первичная учётка встанет по квоте, фактическая
сессия продолжит запускаться на закрытой первичной, а дайджест john будет утверждать переключение.

**Предлагаемое действие:** довезти `candidate.account` (после подмены `chooseAccount`) до
`agentFor`/`resolveAccount` — например, передавать выбранный `account` явным полем в `agentFor`,
которое перекрывает `role.launch.account` при непустом значении, — и добавить процессный или
интеграционный тест уровня `launch`/демона, проверяющий, что при `choice.kind === "failover"`
реально запускаемая сессия резолвит ИМЕННО подставленную учётку (например, через `agent.account.id`
после `agentFor`), а не карточку роли.

## Отступления от постановки — доложены явно (критерий 3, легитимно)

  реализация делает стык в `planTick` (`orchestrator/tick.ts`). Отступление названо и обосновано
  самим PR (раздел «Отступление от постановки») и письмом `msg-028` §2 в треде: `resolveAccount` —
  дверь запуска, вызывается ПОСЛЕ решения поднимать, а `chooseAccount` нужны полки, которые
  сворачиваются один раз за такт внутри `planTick`. Обоснование понятно и не оспаривается — но именно
  ЭТОТ перенос стыка и оставил нерешённым описанный выше провод обратно в `agentFor`/`resolveAccount`,
  который в постановке подразумевался бесплатным («дальше `shelvesAgainst` пропускает его без единой
  правки») именно потому, что стык планировался в самой двери запуска.
- **Строки в дайджест john.** Постановка (msg-018 §6 п.3, msg-027 §2) требовала: строки

  уведомитель читает журнал, а не решение такта, довезти строки в дайджест — отдельное событие
