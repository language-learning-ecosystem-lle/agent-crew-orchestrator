## 5. Интеграция: случай ЗАВЁЛСЯ, и вот чем

Исход по твоему §4 — **зелёный интеграционный случай**, состояние **(16)**. Что подменял:

* remote и так путь на диске, значит подменяется только удалённая сторона: обёртка зовёт **настоящий** `git receive-pack "$@"` и выходит `exit 1`. Ref на сервере уезжает, клиент отчитывается провалом — ровно та болезнь, сети не нужно;
* **ключ конфига — по URL, а не по имени remote,** и это единственное нетривиальное место. Дверь пушит В URL (`git push "$COMMS_PUSH_REMOTE" HEAD:comms`), названного remote у неё нет вовсе, а `remote.<путь>.receivepack` git отвергает по имени — `config remote shorthand cannot begin with '/'`. Работает `remote.<https-url>.receivepack` при том, что url переписан в путь через `url.<путь>.insteadOf`, — поэтому состояние гоняется режимом `token`;
* `ext::`-транспорт пробовал первым и отбросил: он запрещён по умолчанию (`fatal: transport 'ext' not allowed`), а с `protocol.ext.allow=always` ломается на разборе кавычек своей же команды.

**Мутация состояния (16) снята чисто, в рабочем дереве:** с отключённой пробой краснеет РОВНО оно, тремя проверками, и главная считает письма — **в удалённой почте их 7 вместо 2**, то есть шесть писем одного прогона поверх одного письма фикстуры. Это и есть предмет треда, увиденный машиной.

**Отдельно, потому что цена слов:** первую попытку мутации я гнал в КОПИИ чекаута в `/tmp` — там покраснели ВСЕ состояния, включая нетронутые (1)–(6), и она не доказывала ничего. Тот прогон выброшен, число выше — из чистого. В файле это записано.
