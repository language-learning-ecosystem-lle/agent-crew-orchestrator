## Замер (шаг 1) — вывод подтвердился НАПОЛОВИНУ, и вторую половину надо назвать точно

Стенд `gh` из `gate.process.test.ts` (#331) перенесён в стенд яруса: отказ по ИМЕНИ пути `repository.pullRequest.statusCheckRollup.contexts.nodes.0`, ответ без узла. На коде `main` (`5126baae`), до всякой правки:

- **дешёвая половина не задета** — `pr list --json number,headRefOid,body,mergeable,labels` этого узла не просит и отвечает как всегда. Очередь не портится, `open()` не бросает;
- **дорогая бросает на КАЖДОМ PR**, и `readMergeReady` это ЛОВИТ. Нота есть, дословно: `merge-ready: PR #154 (019-operator-ux) not read — Command failed: gh pr view 154 --json number,headRefOid,body,statusCheckRollup,reviews,commits,files,mergeable,mergeStateStatus`;
- **ярус не стреляет ни по кому** — и так каждый тик, пока токен тот же, то есть навсегда;
- **счётчик простоя молчит ПО ПОСТРОЕНИЮ.** `MergeReadyReading.refusal` ставится только на отказе ДЕШЁВОЙ половины («весь ярус погас»), а она отвечает. Значит `foldGhOutage` серии не видит, порог `GH_OUTAGE_TICKS` не набирается, уведомитель не звонит ни разу и `snapshot` про ярус ничего не говорит.

**Поэтому «деградирует молча, без ноты» — верно по существу и неверно по букве, и разница чинится по-разному.** Нота была: одна на PR на тик, в потоке демона. Не было двух других вещей — (1) подстановки: ярус мёртв ЦЕЛИКОМ, а не «нет ускорения на этом PR», и (2) различения в случае, где второй спрос удался, а подставленный источник отказал. Второе — то самое несущее из §2: гарды 1-2 тогда не держатся, ярус не молчит про «нет доступа»… он молчит вообще, потому что **молчание здесь и есть отчёт «не готов»**. Красный PR и слепой токен оставляли ровно один и тот же след — никакого.

Так что чинить было что: PR открыт.

## Починка — #333, голова `56462eb5dce4080cde0d6d1790345f9742cf9a9e`

Тем же способом, что дверь: первый спрос с узлом → отказ опознаётся по пути, который назвал GitHub (`forbiddenChecksRollup`, не по слову — эхо командной строки несёт `statusCheckRollup` в любом падении) → второй спрос без узла → чеки из `actions/runs?head_sha=` через `readReviewRuns` + `checksFromWorkflowRuns`.

**Отказ помнится всю жизнь источника** (демон строит его на старте): 403 оплачивается один раз, а не по PR на тик.

**Цену называю отдельно, потому что она спорит с записанным ограничением яруса.** «Actions-вызов на PR на тик — слишком дорого для подсказки» остаётся в силе для ЯКОРЯ гарда 1 и не тронуто. Здесь вызов платится ТОЛЬКО на контуре, где ролап запрещён, и альтернатива ему там — не более дешёвый ярус, а его отсутствие. Где ролап отвечает (этот репозиторий и любой публичный) — ни одного лишнего вызова. Если это чтение цены расходится с постановкой — скажи, откачу до «подстановки нет, только нота».

Оба источника отказали → `merge-ready: PR #N (<тред>) — the checks were NOT READ: … This is 'no access', NOT 'not ready'`. **Порядок очереди не тронут нигде:** одностороннюю деградацию починка не ослабляет, снимает только немоту.

## Проверяемость — по твоему разделу, все три пункта

- **процессный тест на стыке**, два состояния: подстановка удалась (ярус поднимает тред; в логе стенда — первый спрос с узлом, второй без, ОДИН `actions/runs?head_sha=`) и оба отказали (ярус называет «не прочитано», и говорит это ВНЕ картинки);
- **юнит** на трёх состояниях решения яруса: `refused` → нота «no access»; честно красные чеки → молчание, как и было; `substituted` → ярус стреляет и своей жалобы не добавляет;
- **живая приёмка на приватном — не покрыта**, причина твоя и я её не переписываю.

**Доказано мутацией:** обратное применение диффа правки при тестах на месте даёт три красных из новых (оба процессных + юнит на `refused`). Четвёртый (`substituted`) зелен и без правки — он сторож формы, а не доказательство.

Стенд разбирает вызовы по `"$*"`, а не по `$2`: `gh api repos/…` кладёт URL туда, где `pr view` кладёт подкоманду, и позиционный разбор увёл бы подставленный спрос в ветку по умолчанию.
