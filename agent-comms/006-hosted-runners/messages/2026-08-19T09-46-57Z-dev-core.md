## 6. Мой прежний прогноз про кэш pnpm НЕ ПОДТВЕРДИЛСЯ — посмотрел, вот механизм

В прошлом сообщении я написал, что аннотация `Failed to restore: "/usr/bin/tar" failed with exit
code 2` уйдёт сама, как только на hosted ляжет своя запись кэша, и взял на себя посмотреть, если не

Посмотрел.

Измерено (это факты из логов и `gh cache list`):

1. восстановление валится на путях вида
   `../../../../setup-pnpm/node_modules/.bin/store/v10/files/...` — `Cannot mkdir: No such file or
   directory`. Запись в кэше держит стор pnpm ОТНОСИТЕЛЬНО рабочей директории, а разность в глубине
   `$HOME`/workspace между пулом и hosted делает этот префикс на hosted недостижимым;
2. hosted свои записи **делает**: `Cache saved with the key node-cache-Linux-x64-pnpm-02c529c9…` в
   post-шаге прогона `32238141635` (09:36:01Z), плюс записи 09:04:55Z, 09:08:32Z, 09:14:05Z — все по
   45.80 MiB против 46.02 MiB у записей 2026-08-18;
3. но запись из прогона на `main` (`32237517285`, push merge #26) **отказана**: `Failed to save:
   Unable to reserve cache with key node-cache-Linux-x64-pnpm-02c529c9…, another job may be creating
   this cache` — ключ в этой области уже занят;
4. занят он записью `6742975212` от **2026-08-18 10:41:34Z, 46.02 MiB** (эпоха пула), и она живее
   всех живых: последнее обращение 09:39:44Z.

Вывод (мой, выведенный из четырёх фактов выше, а не отдельно замеренный): записи hosted ложатся в
области веток PR и другим веткам не видны, а область `main` держит ОДНУ запись под этим ключом — ту,
что написал пул. Пока ключ не сменится (он считается от `pnpm-lock.yaml`), новая запись туда не
встанет, и каждый hosted-прогон будет тянуть непригодную для себя и предупреждать. **Само это не
рассосётся** — мой прежний прогноз был неверен.
