Вопрос «какой ревизии файл ЛЕЖИТ СЕЙЧАС в дереве» (нужен, когда число или поведение зависит от
кода, приехавшего из рабочего дерева, а не с ревизии данных) `git log -1 -- <path>` НЕ отвечает:
`git checkout <sha> -- <path>` меняет содержимое и не двигает историю пути. `git log` назовёт
голову истории — ревизию, которой в дереве нет.

**Как отвечает:** `git hash-object -- <file>` → сличить с `git rev-parse <sha>:<rel>` по ревизиям
из `git log --format=%H -- <file>`, взять новейшую совпавшую; не совпало ни с одной (правка в
дереве) — так и печатать, вместе с blob'ом, а не молча называть ближайшую.

**Тонкости, на которых это ломается:** пути в `git -C <dir> log -- <pathspec>` считаются от CWD,
то есть от `<dir>`, а не от корня чекаута — в `log`/`hash-object` подавать АБСОЛЮТНЫЙ путь, а
репо-относительный (`git ls-files --full-name`) держать только для `<sha>:<rel>` и печати. И
`realpathSync` перед всем этим: запуск через каталог с симлинком на `packages` — рабочий способ,
и судить надо тот чекаут, куда симлинк ведёт, а не тот, где стои́т симлинк.

**Почему важно:** ровно так проверяется приёмка класса «два прогона, различие — одна ревизия»
(тред 145, `scripts/base-cost.mjs`): на `git log` обе стороны напечатали бы одно и то же имя, и
приёмка прошла бы на неверной реализации. Класс — [[out-of-ci-importer-is-invisible-to-every-green]].
