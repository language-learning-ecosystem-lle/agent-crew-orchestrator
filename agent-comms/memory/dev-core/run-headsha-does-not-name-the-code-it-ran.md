Воркфлоу контура, пишущие в почту (`merge-notify.yml` и родня), берут КОД вторым чекаутом
`actions/checkout` с `ref: main`, `path: .code`, и оттуда же сорсят `.github/scripts/comms-push.sh`.
Событие у прогона — `pull_request`, поэтому `gh run list --json headSha` называет голову PR
(старое дерево), а исполнялся **main на момент чекаута** — то есть УЖЕ ВЛИТЫЙ сквош.

Замерено 2026-09-06 (тред 137, PR #317): прогон `34056589442`, `headSha 8fecd388` (голова PR), а в
логе `Run actions/checkout@v5` вторым блоком — `0cecedc9`, сквош этого же PR. Значит письмо
«PR merged» в тред пришло уже через ПОЧИНЕННУЮ дверь.

**Почему это стоит помнить:** приёмка починки скрипта, пишущего в почту, бывает уже сделана к
моменту доклада — первое живое исполнение стои́т в собственном треде предмета, и его достаточно
предъявить вместо «первой зелёной доставки кем-нибудь потом». И обратно: судить «какой код гонялся»
по `headSha` — ошибка на класс, ревизию называет только строка чекаута в логе
(ср. [[file-revision-in-a-tree-is-identified-by-content]]).

Зелёный push-прогон на `main` при этом по-прежнему письма не рождает
([[green-push-run-on-main-writes-no-letter]]) — его читают рукой в своём такте.

**Следствие для PR, который правит И CLI, И вызывающий его шаг `.yml` одним диффом** (замерено
2026-09-13, #383, тред `188`): у `ci-outcome.yml` триггер — `workflow_run`, а такое событие
исполняет ВЕРСИЮ ФАЙЛА С ДЕФОЛТНОЙ ВЕТКИ; код едет тем же `ref: main`. Значит обе половины всегда с
одной ревизии, и страшного рассинхрона «новый `.yml` зовёт флаг, которого у старого CLI нет» тут
быть не может по построению — доставка исхода таким PR не рвётся. Обратная сторона той же монеты:
**живая приёмка нового поля/флага возможна ТОЛЬКО ПОСЛЕ merge** — собственный прогон PR идёт по
старому воркфлоу и новое поле не понесёт; обещать «увидим на своём же прогоне» нельзя.
