Замер 2026-09-05 (тред `099`, предмет C): среда живого `orchestrator up` (пользователь
`aco-hetzner`) токенов НЕ держит — `/proc/<pid>/environ` без `GH_TOKEN`/`GITHUB_TOKEN`. Но
`platformEnvOf({repo})` читает `secrets.env` машинного конфига и отдаёт `GH_TOKEN` «← the secrets
file», `refusal: none`, и push в `comms` с этой средой проходит. То есть «в среде демона токенов
нет» НЕ значит «демон не может писать в почту».

**Why:** вывод «писателя почты у демона быть не может» напрашивается из пустой среды процесса и
он неверен; дверь кредов вычисляет среду дочернего вызова из конфига, а не наследует её.

**How to apply:** мерить не средой, а дверью, из ВРЕМЕННОГО клона (почту руками не трогать — R3), и
обязательно сняв свои токены (`env -u GH_TOKEN -u GITHUB_TOKEN`), иначе зелёное доказывает токен
сессии — см. [[green-on-the-box-may-lean-on-the-box-token]]. **Реф выбирать тот, который ПРИШЛОСЬ БЫ
записать:** `push --dry-run origin HEAD:refs/heads/<новое-имя>` отвечает `* [new branch] …`, то есть
переговоры дошли до согласия на запись, — а `HEAD:comms` на актуальном клоне отдаёт
`Everything up-to-date` и может оборваться на рекламе рефов, оставляя запись выведенной. Контроль
обязателен: тот же реф без токена обязан дать `could not read Username`. `--dry-run` рефа не
создаёт — проверять `git ls-remote --heads … <имя>` (0 строк). Что этим НЕ доказано: что в почту
сходил САМ демон, — это доказывает только живой вызов.
