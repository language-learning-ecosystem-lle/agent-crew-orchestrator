Новый тест, зелёный рядом с новой логикой, покрытия НЕ доказывает: он мог сработать на уже
существовавшем в коде исключении, а фикстура — противоречить собственному комментарию (комментарий
обещал «строки в состоянии уже нет», фикстура эту строку клала). Проверка одна: временно отключить
собственный механизм (`if (false && …)` на новой ветке) и посмотреть, ПАДАЕТ ли именно твой тест.
Падает чужой — тест не про обещанное.

**Why:** ревьюер нашёл это в моём диффе (PR #275, тред 129) мутацией за минуту; сюита из 3557
зелёных тестов такого не видит вовсе — оба состояния для неё одинаково зелены.

**Форма мутации для правки ТЕКСТА (промпт, шаблон письма), где `if (false && …)` некуда вставить:**
`git diff -- <файл> > $M/p.patch` в каталог из `TMPDIR=/tmp mktemp -d` → `git checkout -- <файл>` →
прогон → `git apply $M/p.patch`. Отключает правку целиком, включая комментарий, и восстанавливается
дословно; в отчёт идут ОБА числа — сколько новых упало и сколько прежних осталось зелёными.

**Исключение — случай `not.toContain`, и его надо назвать вслух, а не «починить».** Тест, чьё
утверждение ОТРИЦАТЕЛЬНОЕ («правка не приклеилась там, где не должна»), мутацией своей правки НЕ
краснеет и не обязан: он сторожит противоположное направление — переобогащение, — и зелен в обе
стороны by design. Мерять надо весь набор: сколько случаев покраснело и какие именно остались
зелёными, с причиной. Полевой случай: тред 140, PR #298 — три случая, красных при реверте два.

**How to apply:** перед отправкой PR с тестом на НОВЫЙ механизм прогнать мутацию своей правки; если
тест выжил — либо переписать его так, чтобы он мерил ту половину, которой раньше не было (обычно это
второй такт / второй вызов, а не первый), либо назвать его сторожем обратного направления по
абзацу выше. А расхождение, которое мутация вскрыла, но чинить нельзя,
объявлять границей в трёх местах: комментарий кода, комментарий теста с ровно этим входом, дока.
