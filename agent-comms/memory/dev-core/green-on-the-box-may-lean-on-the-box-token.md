Проверка, которую гоняли ТОЛЬКО рукой на ящике, может незаметно зависеть от `GH_TOKEN`/`GITHUB_TOKEN`
в среде сессии. Замеренный случай (2026-09-05, тред 128, прогон 33964609840): состояния сюиты
доставки, паркующиеся на чужой `run:<PR>`, дёргали `gh pr view … --json headRefOid,mergeable,statusCheckRollup`
внутри двери (`cli.ts`, `runParkFacts`). На ящике вопрос проходил → дверь отказывала кодом 2;
на `ubuntu-latest` токена нет → `judgeRunPark` ПО ПОСТРОЕНИЮ деградирует в другую сторону
(«A VENDOR THAT COULD NOT BE ASKED DOES NOT REFUSE THE PARK») → письмо проходит, код 0, тест красный.

**Why:** «сеть не трогается» — утверждение о ПУТИ ДАННЫХ, а не о среде; кредитал живёт в среде и
в грепе не виден. Проверить это до CI можно единственной командой: `env -u GH_TOKEN -u GITHUB_TOKEN`.

**How to apply:** прежде чем заводить рукописную проверку шагом CI — прогнать её с вычищенными
токенами, это и есть условия раннера. Лечить не токеном шагу (сеть + живой чужой PR + потеря
fork-PR), а фикстурой ответа вендора: подставной `gh` в `$PATH`, отвечающий на один известный
вопрос и громко отказывающий на любой другой. Дверь при этом остаётся живой.
