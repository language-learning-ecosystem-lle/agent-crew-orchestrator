`gh api ... --jq '<фильтр>'` при ошибке САМОГО ФИЛЬТРА выходит кодом 1, ровно как при отказе
сети. Идиома `X="$(gh api … --jq …)" || X='?'` в шелле воркфлоу поэтому объявляет чужую систему
виновной в собственном дефекте, и читатель уходит проверять исправную сторону.

Ловушка, которая это породила (`notifier-watch.yml:203`, 2026-09-03): `["a","b"] | index(.conclusion)`
— `.` справа от `|` это МАССИВ-литерал, не входной объект; в движке `--jq` (gojq) это тип-ошибка
ПРИ ЛЮБЫХ данных. Ветвь «не прочитано» становится единственной достижимой, а рабочие ветви —
мёртвыми. Правильно — связать переменную ДО пайпа: `select(.conclusion as $c | [...] | index($c))`.

**Why:** ветвь отказа не краснит прогон (по замыслу — доставка важнее телеметрии), поэтому
дефект живёт до первого, кто прочитает текст письма и НЕ поверит ему.

**How to apply:** текст отказа, называющий внешнюю систему, сверять со строкой ошибки в логе
прогона — они разошлись, значит виноват свой фильтр. Независимость от данных доказывается
запуском того же фильтра на заведомо чужом входе (`gh api /rate_limit --jq '…'`): та же ошибка =
дефект фильтра, а не редкий случай. Смежное — [[door-defects-hide-in-process-tests]],
[[yaml-step-body-is-testable-when-extracted]].
