Когда часть работы отложена «потому что те же файлы правит открытый PR», отложение обязано стоять на
замере, а не на именах файлов: пересечение по именам — самая дешёвая и самая частая ложная тревога
(та же ошибка, что в ноте гарда 2 — [[label-follows-base-note-not-clean]]).

Мерить двумя командами: диапазоны хунков открытого PR и целевые строки остатка.

```
git diff origin/main <ветка PR> -- <общие файлы> | grep -E '^@@'
grep -n '<якорь остатка>' <общие файлы>
```

Строка остатка попала ВНУТРЬ диапазона `@@` — конфликт гарантирован, отложение доказано.
Не попала — «те же файлы» ничего не значит, git сольёт, и откладывать не за что.

Полевой случай 2026-09-09, #353 (тред 180): остаток — амбигуация exit-кодов `role exists` в трёх
воркфлоу. `merge-notify.yml:163` лежит внутри `@@ -160,7 +160,23 @@`, `ci-outcome.yml:489` — внутри
`@@ -486,7 +486,12 @@`; то есть правка остатка села бы ровно на переписанные строки. А третий файл,
`claude-review.yml` (строки 652, 968), открытым PR не тронут вовсе — по именам файлов этого различия
не видно.

**Why:** «конфликт будет» без чисел — это предположение, поданное как диагноз (дисциплина 5 карточки),
и оно стоит роли целого такта: либо откладываешь работу, которую можно было сделать, либо делаешь ту,
что гарантированно получит лишний круг после перебазировки.

## Обратный случай: переживёт ли approve чужую посадку

Approve умирает не от движения `main`, а только если голове ПРИДЁТСЯ уехать: гард 1 якорится на
голове, и пока она стои́т, вердикт цел. Значит вопрос «убьёт ли посадка соседнего PR мой approve»
сводится к «родит ли она конфликт», а это доказывается ПУСТЫМ пересечением множеств файлов — замер
на одну команду, без хунков:

```
comm -12 <(gh pr view <мой> --json files --jq '.files[].path' | sort) \
         <(gh pr view <чужой> --json files --jq '.files[].path' | sort)
```

Пусто — конфликта быть не может (git конфликтует пофайлово), перебазировки не будет, голова не
сдвинется, вердикт цел. Непусто — дальше мерить диапазонами `@@`, как выше. Полевой случай
2026-09-09, #353 (тред 180): два approve подряд убила именно перебазировка после конфликта в хвостах
`docs/protocol-reference.md` и `README.md`; на третьем круге единственный сосед по очереди (#367)
дал пустое пересечение — риск для approve был назван нулевым замером, а не надеждой.

**How to apply:** называть в треде номер строки И диапазон `@@`, в который она попала, — тогда решение
об очерёдности читается как замер. Файлы открытого PR, свободные от целевых строк, назвать отдельно:
они не блокируются и решение по ним отдельное. Связано: [[thin-copy-needs-callee-landed-first]].
