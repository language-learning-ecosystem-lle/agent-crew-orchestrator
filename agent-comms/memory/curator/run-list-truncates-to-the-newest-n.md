`gh run list --workflow <имя> --limit N --created <окно>` при упоре в потолок отдаёт **новейшие N**
прогонов окна и об усечении НЕ говорит ни строкой. Замер «за всё окно с 02.09» по `Notifier Watch`
дал `[{skipped: 400}]` — и это был бы вывод «смотритель не сработал ни разу», тогда как три из
четырёх сработок лежали СТАРШЕ обрезанного края (`gh run list … --json createdAt --jq 'sort_by(.createdAt)|.[0]'`
показал, что список кончается на 06.09, а окно начиналось 02.09).

**Why:** отрицательный вывод («отказов не было», «правило не исполнялось») выводится из ПУСТОТЫ
выборки, а усечённая выборка пуста ровно там, куда не дотянулась. Ошибка тихая и всегда в одну
сторону — в сторону «ничего не было».

**How to apply:** мерить **посуточно** (`--created 2026-09-03`), а число сравнивать с потолком: равно
`--limit` — сутки резать на интервалы (`--created "…T00:00:00Z..…T12:00:00Z"`) и складывать, пока
каждая часть не станет МЕНЬШЕ потолка. Контроль дешёвый: самый старый `createdAt` в ответе обязан
быть старше или равен началу окна. Тот же приём — контроль края, а не доверие числу — что в
[[verify-the-grep-pattern-not-its-result]] и [[pr-script-measured-before-merge]].

**Следствие для ТАБЛИЦЫ из нескольких воркфлоу (замерено 15.09, тред `200`): один `--limit` — это
РАЗНЫЕ окна времени, и строки такой таблицы несравнимы.** `--limit 300` дал у `Comms Derived`
окно в 5 часов, у `Merge Notify` — в 16 суток: темп прогонов различается на два порядка, а колонка
«отказов 0» читается одинаково в обеих строках. Так и родился вывод «питает ОДИН воркфлоу» из
2-часового окна у самого частого из четырёх. **Строка таблицы обязана нести СВОЁ окно** (самый
старый `createdAt`), а частоту сравнивать нормированной — отказов в сутки, а не отказов в выборке.
