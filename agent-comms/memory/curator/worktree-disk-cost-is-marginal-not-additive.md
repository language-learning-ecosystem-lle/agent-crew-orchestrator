`du -sh` по ОДНОМУ рабочему дереву печатает **165M**, но из них **153M — жёсткие ссылки на общий
набор `node_modules`**, который держат и все соседние деревья. Выигрыш от удаления = сколько
освободится, ПОКА ОСТАЛЬНЫЕ СТОЯТ, и он считается только разностью двух наборов:

```
du -csh <всё, что останется>            # A
du -csh <всё, что останется> <кандидат> # B   → цена кандидата = B − A
```

**Замер 17.09 (`hetzner`, `.worktrees` = 1.5G), которым это поймано:** ОДНИ И ТЕ ЖЕ три дерева
старого образца (`curator`, `dev-core`, `devops`) дают ТРИ числа, и разброс между крайними — 15 раз:

| способ | число |
| --- | --- |
| сумма построчных `du -sk --count-links` | **524M** |
| один прогон `du -csh` по набору (дедуп ВНУТРИ набора) | **187M** |
| `du(.worktrees)` − `du(.worktrees без набора)` — сколько ОСВОБОДИТСЯ | **35M** |

**Один прогон `du` по набору — тоже завышение, а не «правильный» ответ:** он дедуплицирует внутри
набора, но ссылки, уходящие к тому, что ОСТАЁТСЯ, считает как свои. На большом наборе завышение
никуда не девается: по всем попарным деревьям `du` одним прогоном — 1173M, маржинально — 1023M,
разница **150M**. Верен только третий способ. Брать разность шире (от корня контура, с `.git` и
`node_modules` главного чекаута) смысла нет — замерено, число то же.

**Цена самого замера — 0.3 с** на полный прогон `du` по `.worktrees` (прогретый кэш): «дорого» не
довод против маржинального итога.

**Практическое следствие для любой описи и любого решения об уборке:** итог печатается
маржинальным и называет, относительно какого остатка он посчитан. Аддитивная сумма по строкам
описи завышает выигрыш и ровно то число, по которому решение и принимается.

Обратная сторона того же: «снести только `node_modules`, деревья оставить» возвращает как раз
общий набор и оставляет опись прежней длины.
