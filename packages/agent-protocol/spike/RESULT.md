# P0 — результат спайка headless-цикла

Тред 012, фаза P0. Прогон: `bash packages/agent-protocol/spike/headless-cycle.sh`.

## Что доказано

**Headless-агент проходит ПОЛНЫЙ цикл протокола, а не только отвечает как команда.** Не гипотеза — факт, проверенный в origin после прогона (не по рапорту агента):

| проверка | результат |
|---|---|
| процесс `claude -p` вышел кодом 0 | ✓ |
| msg-002 записан агентом в тред | ✓ |
| msg-001 сохранён — append-only не сломан | ✓ |
| ход передан curator в INDEX (агент прогнал `rebuild-index.sh`) | ✓ |

**Три прогона подряд — все 4/4.** Стабильно после устранения трёх дефектов стенда (ниже). `subtype=success`, `session_id` возвращается, `num_turns` 8–13.

N=3 достаточно для P0 (доказательство механики: «headless проходит цикл» — да/нет). Но это НЕ мера надёжности: до фикса дефектов стенда та же связка давала 4/4 → 3/4 → 1/4. Если число ляжет в основу решений P3 (частота опроса, экономика, ретраи) — гонять кратно больше и на разной нагрузке, а не опираться на N=3 (замечание ревьюера по PR #17).

Отдельно, вне этого скрипта, проверена **непрерывность через `--resume`**: первый headless-прогон «запомни сорок два» → второй прогон отдельным процессом «какое число?» → `42`. Контекст переживает завершение процесса — то, на чём держится замена живой вахты.

## Следствие для модели исполнения

Если пробуждение агента = запуск `claude -p` на непустой почте, то **исчезает целый слой**: tmux-сессия, живая `wait-for-mail`, `/wake`, сторож-как-будильник. Вместе с ним — класс багов «сессия жива ≠ агент видит почту» (боль 5, тред 008): в модели «пробуждение = новый процесс» его не существует.

## Экономика (ответ на п.6 постановки)

Реальный цикл (разбор треда, запись ответа, rebuild, коммит, push): **~$0.32 за цикл**, ~30 с, ~6k output-токенов, ~283k cache-read. Это порядок величины, не точная смета: тривиальный `PONG` стоил $0.068, реальный разбор — в ~5 раз дороже. При частых пробуждениях это статья расходов, и к P3 нужна прикидка частоты опроса и решение подписка-vs-API-ключ.

## Три дефекта стенда — и почему это главная находка

Первые прогоны давали то 4/4, то 3/4, то 1/4. Соблазн был списать на «агент недетерминирован». **Ни один из трёх сбоев не был в агенте — все три в харнессе:**

1. **Молчаливое копирование `rebuild-index.sh`** (`cp … 2>/dev/null || …`): в одной из версий путь не резолвился, скрипт не попадал в песочницу, агент видел пустой `bin/` и импровизировал (правил INDEX руками — иногда удачно). Провал списался бы на агента. Фикс: явный поиск + громкое падение.
2. **Нецифровое имя тестового треда** (`T01-spike`): генератор берёт только `[0-9][0-9][0-9]-*` и молча игнорировал тред — `waiting-on` выходил пустым. Фикс: `900-spike`.
3. **PATH-зависимость `claude`**: голый вызов по имени давал `exit 127` в под-шелле без nvm-bin. Фикс: явный резолв бинаря + громкое падение до цикла.

Урок ровно тот, что мотивирует весь пакет (боли 1–6): **команда, молча зависящая от окружения, даёт результат, неотличимый от дефекта проверяемого.** Три раза подряд на одном спайке — не случайность, а системная причина существования `agent-protocol`. И правило, которое из этого следует для самого пакета: **не путать дефект харнесса с дефектом проверяемого — сначала проверить стенд фактом.**

## Что это НЕ доказывает

- Что headless надёжен под нагрузкой/параллелью — гоняли последовательно, по одному.
- Что свободный текст агента всегда попадает в формат — наоборот, спайк показал, что попадает НЕ всегда (агент импровизировал вокруг сломанного стенда). Это прямой аргумент за P2 (операции над тредами как API с валидацией, а не клейка markdown): агент должен вызывать команду, а не воспроизводить формат по памяти.
- Cursor headless — не проверялся (дверь, не реализация).
