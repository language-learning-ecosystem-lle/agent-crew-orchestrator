# agent-protocol

Файловый протокол координации автономных агентов поверх git: роли и права,
операции над тредами и реестром, вахта/пробуждение/уведомления, инициализация
на новом проекте.

**Статус: фаза P2, тред `012-agent-protocol-package`.** Сделано: каркас,
ролевая модель как данные (P1), модель треда «одно сообщение — один файл» с
генератором производных, валидатором и миграцией (P2, ядро). Дальше:
переключение живого контура на пакет, исполнительный слой (P3), init на новом
проекте (P4).

## Дисциплина выносимости

Пакет живёт в монорепо, но **проектируется как чужой**: он уедет в отдельный
репозиторий и будет переиспользоваться. Отсюда правила с первого коммита:

- нейтральное имя `agent-protocol` — **без скоупа проекта**. В этом репозитории
  все workspace-пакеты живут под `@lle/`; здесь скоуп сознательно не ставится,
  иначе переезд начинался бы с переименования, а имя пакета — самое ссылаемое,
  что в нём есть;
- **ноль знания о проекте**: ни одного импорта из `apps/*`, ни предметной
  области, ни путей конкретного репозитория в коде. Всё проектное приходит
  снаружи — конфигом и аргументами команд;
- транспорт уведомлений (Telegram и пр.) — **отдельный пакет**: ядро порождает
  события, доставку берёт на себя подключаемый плагин. Тексты уведомлений тоже
  не здесь — это язык конкретной команды;
- переезд должен быть механическим (`git subtree split` + замена
  workspace-зависимости на версию из реестра).

Storage-абстракция (`git-local` / `github-api`), MCP-сервер пакета и требование
runtime-agnostic ядра **сняты** решением john от 2026-07-23 вместе с переходом
на модель «одно сообщение — один файл»: запись перестала быть операцией пакета,
а генерация производных всегда идёт в Node с чекаутом.

## Ролевая модель как данные (P1)

До этого роли жили прозой в `ROLES.md`, а поведение выводилось из неё глазами
и bash-скриптами: список ролей вырезался awk'ом из markdown-таблицы, состав
уведомляемых был захардкожен строкой, имя сессии складывалось шаблоном, а «кого
дёргать, чтобы ассистент ожил» жило в комментарии внутри awk-программы.

Теперь роли — конфиг, а поведение из него **выводится**:

| данные | что из них следует |
|---|---|
| `wake.mode = self` | человек: уведомляем напрямую, будить некого |
| `wake.mode = via-human`, `via` | ассистент без своего процесса: зовём названного человека («дёрни его») |
| `wake.mode = watch`, `session` | агент с сессией: его будит сторож, имя сессии — оттуда же |
| `wake.mode = event` | просыпается от события платформы: ни будить, ни уведомлять |
| `permissions` | кому можно менять `status` треда (принуждение — P2) |
| `status` | активные роли; ушедшие остаются в реестре, иначе старые треды перестают разбираться |

Схема отвергает неизвестные поля: опечатка в имени поля иначе означала бы
молчаливое умолчание — тот самый класс тихих дефектов, ради которого пакет и
пишется.

Проверки связности живут в `createRoleRegistry` и все до одной про реальный
отказ: дубль роли, `via` в никуда или в роль, которую саму некому разбудить,
две роли на одной tmux-сессии (пробуждение уехало бы не туда).

`zones` — единственное поле без кодового потребителя на P1: оно нужно, чтобы
конфиг мог со временем стать источником карточки роли (P4). Отмечено осознанно,
чтобы не выглядело забытым.

## Конфиг протокола

Один файл в корне репозитория, где протокол используется (`agent-protocol.json`
по умолчанию): роли, права, зоны, ветка и каталог почты. Отдельного документа с
таблицей ролей нет — два описания одного набора расходятся по построению.

```
pnpm -F agent-protocol cli config check --ref origin/main
pnpm -F agent-protocol cli roles list   --ref origin/main
pnpm -F agent-protocol cli role exists  --ref HEAD --role dev-core
```

**Читается только через пакет и только по явному `ref`.** Чтение файла с диска
рабочей копии показало бы правку из СВОЕЙ feature-ветки как действующую — тот
же класс, что cwd-слепота, только про права. Умолчания у `ref` нет намеренно:
проверка в CI обязана смотреть на голову ветки PR, контур — на `origin/main`.

Свежесть — часть операции: `origin/*` без `fetch` протухает молча, поэтому
обновление делает сама команда, а `--no-fetch` печатает предупреждение.

`instructions` роли — массив, порядок = порядок чтения (общее правило проекта,
затем ролевая карточка). `kind: external` означает, что текст лежит в репо, но
ИСПОЛНЯЕТСЯ снаружи (скилл на стороне чата) — единственное место, где машинной
гарантии нет, и мы её не обещаем. Объявленный, но отсутствующий на этом ref
файл красит `config check`.

Выход: `0` — сошлось, `1` — расхождение (перечислено построчно), `2` — файл не
прочитан, не JSON или конфиг невалиден. Каждый отказ громкий: урок спайка P0 —
команда, молча зависящая от окружения, даёт результат, неотличимый от дефекта
проверяемого.

## Тред как файлы сообщений (P2)

```
NNN-slug/
  _meta.md            ← источник: title, participants, status
  messages/
    2026-07-23T13-45-12Z-curator.md   ← новое сообщение
    2026-07-21-003-curator.md         ← мигрированное (времени в истории нет)
  _thread.md          ← ПРОИЗВОДНЫЙ: склейка сообщений, для чтения человеком
```

Писатель создаёт свой файл и не трогает чужие — перепечатывание тела, порча
плейсхолдеров и гонки на общем файле исчезают по построению. Взамен появляется
другой риск: правка задним числом становится дешёвой и незаметной. Его держат
два правила — **идентификатор сообщения это имя файла, а не номер** (номер лишь
витрина в собранном треде) и **файл неизменен после коммита**: `check --since <ref>`
поднимает состояние ленты из git и красит любую правку ранее закоммиченного.
Без `--since` проверка неизменности не выполняется и **говорит об этом вслух** —
молчание читалось бы как «проверено и цело».

`waiting-on` — поле заголовка сообщения, а не строка в прозе: полный
остаточный состав, отсутствие поля означает «ход не передаю», `—` — «ожидание
снято». Неизвестная роль в поле **красит проверку**, а не отбрасывается молча:
молчаливый отброс и был механизмом потери роли из объявления.

Обе формы (файлы и старый единый `_thread.md`) читаются одновременно, поэтому
треды переезжают по одному и «дня переключения» не существует.

### Команды

```
agent-protocol index build  --root <comms> --config <roles.json> [--write]
agent-protocol thread build --root <comms> --config <roles.json> --id <NNN-slug> [--write]
agent-protocol check        --root <comms> --config <roles.json> [--since <ref>]
agent-protocol migrate      --root <comms> --config <roles.json> [--id <NNN-slug>] [--write]
agent-protocol mail         --root <comms> --config <roles.json> --role <id>
```

Без `--write` ничего не пишется. `mail` считает почту **из тредов**, а не из
`INDEX.md`: производный реестр может отстать или не собраться, и завязывать на
него вахту значит ослепить контур ровно так, как это уже случалось.

Миграция принимается только с побайтовым гардом: склейка мигрированных файлов
обязана воспроизводить исходный `_thread.md` бит в бит, иначе тред не
переносится. Это то, что делает переписывание append-only ленты допустимым.

Второй отказ миграции — **коллизия имён**: два сообщения с одной ролью, датой и
историческим номером дали бы один файл. Побайтовый гард такую пару не ловит по
построению (он сверяет склейку из разобранных сообщений, а не то, что осталось
бы на диске), поэтому она проверяется отдельно и тоже блокирует запись: иначе
одно сообщение молча затёрло бы другое, а потеря всплыла бы только при
следующей регенерации.

## `spike/` — P0

`headless-cycle.sh` доказывает, что headless-агент (`claude -p`) проходит
полный цикл протокола на изолированном стенде: читает тред, дописывает секцию,
перегенерирует реестр, коммитит и пушит, выходит кодом. Результат и выводы —
`spike/RESULT.md`. Спайк работает только в песочнице `$TMPDIR` и не касается
боевого контура.
