# agent-crew-orchestrator

Протокол координации агентов: файловая почта в git, ролевая модель как данные, оркестратор, поднимающий сессии по факту «тред ждёт роль». Репозиторий generic — про продукт обслуживаемого проекта он не знает ничего.

## Пакеты

| пакет | что это |
| --- | --- |
| `packages/agent-protocol` | ядро: CLI почты (`thread show`, `new-message`, `new-thread`, `thread status`), схема тредов, дверь merge (`merge-gate`), дверь зон (`zones check`), оркестратор (демон, планировщик, `run`, `status`, `tui`, systemd-юнит), уведомитель (`notify`), диагностика (`doctor`, `preflight`, `init`) |
| `packages/transport-telegram` | транспорт уведомлений: доставка в Telegram. Ядро о вендоре не знает — модуль называется в конфиге (`notifications.transport.module`) |

Устройство протокола — `PROTOCOL.md`; поведение кода и справка по командам — `docs/protocol-reference.md` и `packages/agent-protocol/README.md` (раздел «Commands» — единственное описание формы команд); ввод в строй ящика — `docs/box-setup.md`.

## Конфиг живёт НЕ здесь

**Конфиг протокола (`agent-protocol.json`: роли, права, зоны, ветка и каталог почты, тексты уведомлений) лежит в репозитории обслуживаемого проекта, а не в этом.** Так по построению: права роли обязаны меняться через ревью того проекта, чьи это роли, а generic-ядро читает конфиг только по явному ref. Машинно-специфичное — во втором конфиге вне git (`~/.config/agent-protocol/local.json`: пути к бинарям агентов, файл секретов транспорта, имя инстанса).

Отсюда же читается имя юнита демона: `agent-protocol.service` — умолчание пакета, инстанс переопределяет его конфигом.

**Кроме одного случая — этого репозитория самого.** С 2026-08-18 `agent-crew-orchestrator` обслуживает сам себя: роли работают над кодом протокола, значит обслуживаемый проект — он же, и `agent-protocol.json` лежит в его корне **по тому же правилу, а не вопреки ему**. Правило говорит «конфиг живёт там, чьи это роли»; здесь это просто совпало с местом кода. Практическое следствие ровно одно, и оно жёстче обычного: правка конфига здесь меняет контур, который в этот момент работает, — поэтому она идёт кнопкой владельца решения, как любой док власти.

## Почтовые воркфлоу: три живых, два замороженных

Пять почтовых воркфлоу приехали сюда вместе с историей пакета и были заморожены до `on: workflow_dispatch` как эталон происхождения (решение john 2026-08-17, тред `080-extraction-prep`): они читают почту и роли обслуживаемого проекта, которых тогда здесь не было. **Троих этот довод больше не касается** — с тех пор как репозиторий обслуживает сам себя (см. выше), почта, роли и события merge здесь свои. Двое разморожены кнопкой john на PR #6 (2026-08-18, тред `082-hetzner-migration`), третий — ревьюер — решением john 2026-08-19 (тред `014-merge-model`), и его разморозка отдельно стоила решения о расходе:

| воркфлоу | `on:` | состояние |
| --- | --- | --- |
| `comms-derived.yml` | `push: branches: [comms]` (с `paths-ignore` на `_instances/**`) + `workflow_dispatch` | **жив** — собирает производные почты |
| `merge-notify.yml` | `pull_request: types: [closed]` + `workflow_dispatch` | **жив** — merge приезжает в тред; подписывается ролью `github` (объявлена 2026-08-19, до неё дверь почты отказывала и уведомление не ложилось) |
| `ci-outcome.yml` | `workflow_dispatch` | заморожен |
| `notifier-watch.yml` | `workflow_dispatch` | заморожен |
| `claude-review.yml` | `pull_request: types: [labeled]` + `issue_comment: types: [created]` + `workflow_dispatch` (inputs `pr`, `max_turns`) | **жив** — автономный ревьюер по метке `review` или `@claude` в PR; тратит `CLAUDE_CODE_OAUTH_TOKEN` (подписочный токен, секрет положен john рукой) |

Два следствия для роли, обе стороны — из этой же таблицы: **`ci-outcome.yml` заморожен, значит исход CI событием в тред НЕ приезжает** — зелёный на голове роль снимает своей рукой (`gh run list --commit <head>`) ДО передачи хода, а «жду прогон» здесь означает «жду того, чего не будет»; **`merge-notify.yml` жив, значит парковка `parked-on: pr:<n>` законна** и снимается штатно — но живого триггера для этого мало, нужна ещё объявленная роль-подпись, и до 2026-08-19 её не было (четырнадцать красных прогонов подряд, ни одного уведомления в почте: [`docs/install-notes.md`](docs/install-notes.md), §2). Приведённая таблица — не режим, а факт: `.github/workflows/**` правит только john. Оба следствия плюс третье того же класса (ревьюер разморожен → право merge у ролей включается его вердиктом) развёрнуты в надстройке установки — [`docs/install-notes.md`](docs/install-notes.md); там же дата и способ сверки таблицы с `on:`, чтобы следующая сверка стоила одно чтение.

Собственный CI репозитория — один `checks.yml` (`pull_request` + push в `main`): шаг «agent-protocol.json держится» (`config check --ref HEAD`, первым после установки), lint, typecheck, test, шаг `git identity` и шаг «comms-derived синхронен с каноном» (ради него чекаут с `fetch-depth: 0`).

## Доставка пакета наружу: тег-срез, а не `main` (тред 018)

**Чужой репозиторий ставит пакет зависимостью `github:language-learning-ecosystem-lle/agent-crew-orchestrator#<тег>`, а такая зависимость кладёт в `node_modules/agent-protocol` КОРЕНЬ репозитория.** Корень здесь — воркспейс (`"name": "agent-protocol-workspace"`), пакет лежит под `packages/agent-protocol/`, поэтому пин на любую точку `main` дал бы потребителю дерево, в котором нет ни `src/cli.ts`, ни `src/orchestrator/watchdog.ts`. Наружу едет не ветка, а **тег, дерево которого начинается с содержимого `packages/agent-protocol`**.

Режет такой тег `scripts/split-package.sh` (`git subtree split` плюс проверки), и режет его рука на каждом бампе — автоматизация реза трогает `.github/workflows/**` и стоит отдельного решения john:

```
scripts/split-package.sh --tag agent-protocol-v0.2.4 [--prefix packages/agent-protocol] [--ref HEAD] [--base origin/main] [--push]
```

- **Схема имён — `<name>-v<version>` из `package.json` пакета на срезаемой ревизии**, и скрипт отказывает, если имя тега и версия разошлись: тег читает чужой репозиторий, и врать о версии ему нельзя. Практическое следствие — **каждая доставка начинается с бампа `version` в `packages/agent-protocol/package.json`**, иначе следующий рез упрётся в уже существующий тег.
- **Срез обязан нести всю линию `--base` (по умолчанию `origin/main`), и это проверяется дверью, а не глазом.** Рез с головы ветки, чья база отстала, выпускает наружу артефакт БЕЗ уже слитой работы — так `agent-protocol-v0.2.0` уехал без коммита треда 016 (замер 2026-08-21: `git diff` между тегом и срезом с `main` — 13 файлов). Скрипт отказывает, перечисляя недостающие коммиты ПО ИМЕНАМ; лечится это ребейзом ветки бампа на `main`, а `--allow-behind` превращает отказ в такое же громкое предупреждение, если рез с отставшей линии — сознательный. Коммиты линии, не трогающие `--prefix`, отказом не считаются, и скрипт говорит об этом отдельно.
- **Линия `v0.1.x` закрыта.** Тег `agent-protocol-v0.1.1`, на который LLE пинится с 2026-08-18, лежит на дореезданой линии: `git merge-base agent-protocol-v0.1.1 origin/main` пуст, общего предка нет, и раскладка там другая (корень = сам пакет, потому что и репозиторий был другой). Линия `v0.2.x` — первая, срезанная этим скриптом с сегодняшней `main`.
- **Существующий тег не переносится** — на него мог уже сослаться чужой pin; перенос это force-операция, и решает её человек.
- **Рез называет версию схемы, которую пишет тег** (`protocolVersion этот тег пишет: N (из '<путь>')`), повторяет это число в ИТОГОВОЙ строке — той, что копируют в тред как объявление тега, — и печатает готовую команду сверки с потребителем. Срез без `version.ts` назван словами; `version.ts` с нечитаемым объявлением — отказ, тег не создаётся: неизвестное не выдаётся за отсутствующее.
- Без `--push` создаётся только локальный тег, и скрипт печатает команду отправки.

Что получает потребитель (проверено установкой, тред 018): корень `node_modules/agent-protocol` = `package.json README.md spike src tsconfig.json vitest.config.ts`, путь до CLI — `node_modules/agent-protocol/src/cli.ts`, из зависимостей тянется один `zod`. `tsconfig.json` в срезе продолжает ссылаться на `../../tsconfig.base.json`, которого в артефакте нет: `tsx` его не читает и CLI стартует, а `tsc` внутри установленного дерева — сломается. Артефакт предназначен для ЗАПУСКА, не для сборки у потребителя.

### Перед переездом пина — два числа рядом (тред 028)

**Тег несёт не только код: он несёт версию схемы протокола, которую пишет пакет. Пин переезжает только после того, как это число поставлено рядом с `protocolVersion` конфига потребителя — и берутся оба ДО переезда, у КАНДИДАТА, а не у того, что установлено сейчас:**

```
agent-protocol schema version --package-ref agent-protocol-v0.2.3 --repo <репозиторий-потребителя> --ref main
```

Число тега читается **из исходника тега** (`src/schema/version.ts`), без установки и без чекаута; число потребителя — **из сырого конфига, мимо загрузчика**. Вывод называет источник каждого числа словами, поэтому ни одно из них не надо принимать на веру.

**Строка выше исполняется там, где пакет и репозиторий совпадают, — то есть в этом репозитории. У ПОТРЕБИТЕЛЯ она отказывает, пока не назван репозиторий тега:**

```
agent-protocol schema version --package-ref <тег-кандидат> --package-repo <чекаут репозитория пакета> --repo . --ref main
```

Причина не в удобстве флага: тег живёт в репозитории ПАКЕТА, а в `node_modules` потребителя git'а нет вовсе. Без `--package-repo` команда ищет тег у потребителя и отказывает по имени, `exit 2`: `'agent-protocol-v0.2.5' in '<потребитель>' carries none of src/schema/version.ts, packages/agent-protocol/src/schema/version.ts — this ref is not a build of the package (name the repository holding the tag with --package-repo)`. Дешёвый чекаут репозитория тега — `git clone --filter=blob:none --no-checkout --branch <тег> --depth 1` во временный каталог; он же независимо подтверждает sha тега.

**Порядок у потребителя, чей установленный пакет этой команды ещё не несёт: «пин → install → сверка → PR».** `schema version` приехала в `0.2.4`, и контур, запиненный раньше, набрать её из своих `node_modules` не может — там она отвечает полным usage. Сверка при этом всё равно стоит ДО переезда: переезд — это merge, а не строчка в рабочем дереве ветки. Кому нужна сверка ещё раньше правки пина — набирает её из чекаута репозитория пакета.

Замер обеих строк — контур LLE, тред `103-pin-bump-0-2-4`, сообщение `2026-08-22T10-43-28Z-dev-core.md` (первый штатный переезд пина по этому ритуалу, `v0.2.3` → `v0.2.4`); отказ без `--package-repo` воспроизведён 2026-08-28 на теге `agent-protocol-v0.2.5`.

**Прогоняет шаг роль, готовящая бамп** (решение john 2026-08-22, тред 028): штатный переезд пина едет обычным PR-маршрутом контура-потребителя, эта сверка стоит ПЕРВЫМ шагом ветки бампа, и оба числа цитируются в тред постановки. Так предохранители работают до merge, а не постфактум. Рука john — аварийное исключение: красный `main`, когда PR-цикл держит сам себя, плюс кнопки, если конкретный бамп заденет док власти.

Три исхода, и у каждого свой шаг ритуала:

- **числа совпали** — пин едет один, как обычно;
- **потребитель отстал** (конфиг объявляет меньше, чем пишет тег) — **миграция едет ТЕМ ЖЕ PR, что и пин, и пин не уходит в `main` рукой.** Порознь они дают красный `main` у потребителя: свежие `node_modules` отказываются и читать конфиг, и писать в него;
- **потребитель впереди** — пин не переезжает вовсе: пакет стар, даунгрейд не выполняется, и чинится это доставкой нового тега, а не конфигом потребителя.

**В третьем исходе ведущая фраза вердикта написана НЕ про пин — читать её надо мимо, и это осознанно.** Вывод там начинается словами `restart required: … this build is behind the data (pull and restart what is running on it)`: строка одна на двоих — её же печатает гейт загрузчика (`ProtocolVersionError`), и написана она под долгоживущего демона на коде старше данных (тред `023-daemon-parallelism`), где «перезапусти запущенное» и есть починка. В решении о пине запущенного нет: стар не процесс, а тег-кандидат, и починка — взять или срезать тег новее. Верен здесь хвост — «даунгрейд не выполняется». Переписать строку под пин значит ослабить диагноз треда 023 у второго её читателя, поэтому код не трогали (тред 028), а ремонт называет этот текст.

**Расхождение выходит с кодом 0, и это осознанно: шаг — видимое измерение, а не дверь.** Пин живёт в репозитории потребителя, которым этот пакет не владеет, и дверь, обходимая правкой чужого `package.json`, создавала бы ложное чувство гарантии. Код `2` оставлен единственному настоящему дефекту — число НЕ УДАЛОСЬ ПРОЧИТАТЬ (ref не является сборкой пакета, конфиг без `protocolVersion`).

**Почему этого нельзя спросить у `config check`:** он берёт своё число у УСТАНОВЛЕННОГО пакета, а до бампа установлен старый — то есть молчит ровно до момента, когда молчать поздно.

Замер, которым куплен этот шаг (2026-08-22, контур LLE): пин `v0.2.1` → `v0.2.3` рукой прямо в `main`, через 37 секунд красный `CI` на живой `main` — `the repository declares protocol version 17, the package writes 18`. Сдвиг схемы лежал в перепрыгнутой ступени `v0.2.1` → `v0.2.2`, чей заголовок читался как чистый релизный бамп («версия пакета 0.2.1 → 0.2.2»). Правило «число бампается только вместе с миграцией и `protocolVersion` конфига в одном PR» в пакете записано (`src/schema/version.ts`), но оно про СВОЙ репозиторий, который обслуживает сам себя; для чужого контура, куда пакет приезжает тегом с задержкой в несколько ступеней, роль этого правила исполняет шаг выше.
