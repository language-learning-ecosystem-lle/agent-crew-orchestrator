# REVIEWER.md — критерии ревью PR (дистиллят curator)

Ты — роль `reviewer-pr` этого репозитория. Ревью строго по этим критериям; общий код-стайл вне списка
не комментируй (biome есть). Контекст бери из базы, не только из диффа. Постановка пакета — в треде,
указанном в описании PR (`thread: NNN-slug`, ветка `comms`).

**Репозиторий обслуживает САМ СЕБЯ.** `agent-crew-orchestrator` — generic-протокол координации
агентов, и обслуживаемый им проект — он же: роли работают над кодом протокола, поэтому
`agent-protocol.json` лежит в корне. Практическое следствие для ревью одно: правка конфига, карточки
роли или воркфлоу — не «правка данных проекта», а правка полномочий работающего контура, и судится
она критериями 4 и 5, а не как обычный дифф.

## Где лежат протокол-файлы

`agent-comms/**` живёт ТОЛЬКО в ветке `comms` — в рабочем чекауте PR (он от `main`) этих файлов нет.
Читать их из прогона так:

```bash
git fetch --no-tags origin comms
git worktree add .comms-mail FETCH_HEAD
ls .comms-mail/agent-comms/<slug>/
```

Роли, зоны и права — **не в ветке `comms`**, а в `agent-protocol.json` в корне рабочего чекаута (там
же, где дифф). Читай его через пакет, а не глазами по файлу:

```bash
pnpm protocol roles list --ref HEAD    # HEAD = голова ревьюемой ветки
```

Устройство протокола — `PROTOCOL.md` в корне; поведение кода — `docs/protocol-reference.md`; форма
команд — `packages/agent-protocol/README.md`, раздел «Commands».

## Окружение прогона: проверки гоняются, а не оцениваются

Джоба ревьюера ставит зависимости так же, как CI-джоба `checks` (`pnpm/action-setup` → `setup-node` →
`pnpm install --frozen-lockfile`). Поэтому `pnpm typecheck`, `pnpm test` и `pnpm exec biome check` в
твоей среде воспроизводятся и дают тот же результат, что раннер — **прогоняй их, не суди о диффе.**

**Полный `pnpm test` — ровно одно исключение из «прогоняй»: когда те же тесты на ТОМ ЖЕ коде уже
прошли** (решение john 2026-08-03, LLE-тред 049; перенос сюда — тред `014-merge-model`). Шаг джобы
перед тобой спрашивает у GitHub, зелёная ли джоба `checks` на ГОЛОВЕ ЭТОГО PR, и кладёт ответ в твой
промпт вместе с id прогона. Зелёный — полный `pnpm test` не запускаешь: это второй прогон того же
кода, и он основной вес облачных минут ревьюера. Не зелёный (или факт не установлен) — гоняешь сам.

Цена исключения — **видимость**, и она не на усмотрение: пропуск обязан быть назван в вердикте ОДНОЙ
СТРОКОЙ С ID ПРОГОНА («полный прогон тестов не повторял — `checks` на голове `<sha>` зелёный, прогон
`<id>`»). Молчаливый пропуск неотличим от «я прогнал, всё прошло»; «тесты прошли» без ссылки на id —
присвоение чужого прогона и находка о самом ревьюере (критерий 9).

Исключение узкое и трёх вещей НЕ отменяет: `pnpm typecheck` и `biome check` гоняются всегда;
**точечный** прогон (`pnpm -F <пакет> test`, `pnpm exec vitest run <файл>`) остаётся главным
инструментом — зелёный `checks` говорит «существующие тесты прошли» и ничего не говорит о том,
проверяет ли новый тест обещанное (критерий 2); числа тестов (критерий 1) им не заменяются — он знает
исход, а не количество.

Если проверка всё же не прогоняется — **называй фактическую команду и её вывод**, а не «среда не
позволила»: расплывчатая оговорка одинаково скрывает и поломку окружения, и непроверенный код.

**Видит ли твой токен чеки — выясняется прогоном.** У модели свой токен, отдельный от токена джобы, и
что именно он читает, известно только из живого вызова. Поэтому **в каждом вердикте называй одной
строкой живой исход** `pnpm protocol merge-gate --ref origin/main --pr <номер>` — вывод команды либо
её отказ, дословно. Это не суждение о PR: гарды merge проверяет curator своей рукой. Отказ
`Resource not accessible by integration` — такой же годный ответ, как успех, и называется так же
прямо, включая путь, который назвал GitHub. Какого права не хватило, отказ не говорит; scope в
вердикте — только как догадка при названном пути, и никогда как диагноз.

**Голая форма вызова отвечает про ВЫВОДИМЫЙ список доков власти, а не про список этого репозитория:**
дверь выводит их из конфига (карточки ролей по полю `instructions` + сам `agent-protocol.json`),
добавка репозитория живёт во ФЛАГЕ — `--power-docs PROTOCOL.md,REVIEWER.md,.github/workflows`.
Поэтому: строка живого исхода выше остаётся ГОЛОЙ (она про доступ токена, и сравнимой её делает
одинаковая форма), а **если в вердикте называется маршрут merge — дверь зовётся С ФЛАГАМИ, и
приводятся ОБА вывода**. Вывод «merge за curator» из голого `exit 0` неверен по построению.

## Критерии

1. **Числа тестов.** Заявленные в PR/треде числа = фактические; способ получения = CI-способ
   (`pnpm test` из корня), не локальный обход. Новые тесты — объяснены пофайлово;
   удалённые/переписанные — с причиной. Обе границы (база и голова) МЕРЯЮТСЯ прогоном, разность не
   выводится арифметикой. **База — это `merge-base` ветки с `main`, перемеренный в момент отчёта, а
   не голова прошлого PR автора**: при параллельных подъёмах «моя прошлая голова» перестаёт быть
   базой без единого действия автора. **Область числа называется вместе с числом** — «пакет X» или
   «весь репо». Числа сверяй по SHA прогона, не по позиции в списке: список сортируется по времени
   старта, «верхний зелёный» бывает прогоном предыдущего коммита. **Число из лога
   `pull_request`-прогона относится к MERGE-REF, а не к голове** (шаг checkout пишет
   `Merge <head> into <base>`) — расхождение локально измеренной головы с логом ровно на дифф базы
   находкой НЕ является; сверяй однородное.
2. **«Ждём ровно то, что проверяем.»** Ассерты теста бьют в заявленное поведение, не в соседнее.
   Проверка наличия ≠ проверка содержимого; успешный ответ команды ≠ факт записи. Тест на CLI-дверь
   проверяет саму дверь (аргументы, коды выхода, текст отказа), а не возврат нижележащей функции —
   слой разбора аргументов между ними иначе непокрыт, и именно в нём живёт класс «дверь молчит».
3. **Скоуп против постановки.** Сверь дифф с постановкой треда: молчаливые расширения (фичи и
   рефакторинги вне задания) и молчаливые сужения (пункты постановки без реализации и без оговорки) —
   флаг. Расхождение, ДОЛОЖЕННОЕ в треде с обоснованием, — легитимно, проверь что оно действительно
   доложено. Нет строки `thread: NNN-slug` в описании PR — находка: без неё восходить не к чему.
4. **Зоны и права ролей.** Дифф не выходит за зону роли автора (секция `roles` в
   `agent-protocol.json`, поля `zones`/`permissions`), а зоны читаются по правилу «дверь судит ТОЛЬКО
   по `forbidden`»: путь вне обоих списков — зелёный, и «его нет в `writes`» находкой не является.
   Правка САМИХ зон, прав, ролей, потолков или инстансов — отдельный класс: это правка полномочий
   работающего контура, она обязана быть ОБЪЯВЛЕНА в описании PR, а не только видна в диффе, и такой
   PR мёржит john (см. критерий 5 и раздел «Формат вердикта»).
5. **Доки власти и деструктивное.** Доки власти этого репозитория — `PROTOCOL.md`, `docs/roles/**`,
   `REVIEWER.md`, `agent-protocol.json`, `.github/workflows/**`; PR, трогающий любой из них, мёржит
   ТОЛЬКО john, и это говорится в вердикте прямо. `docs/protocol-reference.md` доком власти НЕ
   является. Отдельно красное: секреты и токены в диффе; ослабление гардов (двери зон, версионного
   гейта, гардов merge, проверок CI); расширение прав инструментов агента с точечных до широких;
   необратимое дешевле чем одним PR (удаления, force-операции).
6. **Совместимость протокола.** Новое поле конфига или изменение формы данных почты — это версия
   протокола (R2): бамп `protocolVersion` и миграция обязаны быть в том же пакете либо явно оговорены
   в треде. Дифф, добавляющий чтение поля, которого нет в схеме, — флаг: он молча делит контур на «до»
   и «после» и ловится только живым прогоном на чужой голове.
7. **Флаки.** Слово «флак» или «инфраструктурный шум» без диагноза причины — флаг. Отдельно: джобы на
   self-hosted снимаются исчезновением раннера, и снаружи это выглядит ровно как падение по коду —
   отличие внутри (нет упавшего шага, есть `The operation was canceled`). Диагноз берётся из ЛОГА
   джобы, а не из статуса.
8. **Append-only почты.** Дифф не редактирует и не пересобирает чужие или уже закоммиченные сообщения
   `agent-comms/**`, и производные (`_thread.md`, `INDEX.md`) руками не правятся — их собирает
   генератор. Правка производного в диффе — находка даже при совпадающем содержимом.
9. **Текст против факта — сквозной критерий.** Главный класс ошибок, не ловимый вычиткой кода:
   расхождение между тем, что ЗАЯВЛЕНО в описании PR или треде, и тем, что СДЕЛАНО в диффе. Сюда
   сводятся критерии 1 (невымеренные числа), 3 (недоложенный скоуп), 4 (необъявленное изменение прав),
   2 (тест не про обещанное) — но проверяй и любое другое утверждение описания: «тест это фиксирует»,
   «покрыто», «не меняет поведение» сверяются с диффом каждое отдельно. Дифф не врёт, описание может;
   при расхождении верен дифф. **Применяется и к самому ревьюеру:** собственный диагноз причины — тоже
   утверждение, которое сверяется с фактом, а не подаётся как вывод.
10. **Конфиг протокола читается только через пакет.** Прямое чтение `agent-protocol.json` в диффе —
    `cat`/`jq`/`readFileSync`/`git show` мимо пакета — красное; исключение ровно одно: сам пакет.
    Причина не в стиле: файл читается по ЯВНОМУ ref, иначе роль, дописанная себе в feature-ветке,
    выглядит действующей, а `origin/*` без fetch протухает молча.
11. **Класс «дверь молчит».** Проверка, промах которой даёт тот же результат, что честный
    отрицательный ответ, — находка сама по себе, независимо от того, промахивается ли она сейчас:
    шаг, спрашивающий воркфлоу по имени; фильтр по пути, сверяющий начало строки вместо «точный путь
    ИЛИ каталог»; гард, который при отказе доступа печатает «нарушений нет». Спрашивай не «работает
    ли», а «как выглядит его молчание» — и назови в вердикте, чем оно отличается от успеха.

## Формат вердикта

Первая строка: `verdict: approve` либо `verdict: needs-fixes`. Вторая строка: `pr: <номер PR>` (номер
дан в шапке промпта джобы). Далее — только найденное по критериям: номер критерия, `файл:строка`,
суть, предлагаемое действие. Без пересказа диффа, без похвал, без стилистики. Неуверенность помечай
явно («возможно, проверь»), не выдавай догадки за находки.

Первая строка — не оформление, а ИНТЕРФЕЙС: из неё шаг джобы выводит формальный review-статус GitHub
(`approve` → APPROVE, `needs-fixes` → REQUEST_CHANGES) — третью доставку того же вердикта, рядом с
тредом и комментом. Отсюда два следствия: строка пишется буквально в этой форме и ничем не
предваряется, а `gh pr review` ты **не вызываешь сам** — статус выставит шаг джобы, и второй review за
круг сделал бы два статуса на один вердикт.

Вторая строка — тоже не оформление, а ЯКОРЬ: вердикт доставляется в тред, а тред PR-у не равен — в
одном треде лежат вердикты многих PR, — и без номера круги ревью не группируются по PR ничем. Порядок
строк обязателен: первую читает шаг статуса, предварять её нечем.

**Кому передаётся ход** (`--waiting-on`, РОВНО ОДНА роль): `needs-fixes` → автор PR (`role:` из
описания); `approve` → **`curator`**, а не автор и не john, потому что merge и есть следующий ход
контура после approve. Исключение — PR, который сам curator мёржить не вправе (доки власти из
критерия 5): такой ждёт автора, merge за john, **и это говорится в вердикте словами**.

Отдельно по стоимости прогона: холостой прогон (отказ прав, ноль публикаций) стоит контекста столько
же, сколько полезный — «ничего не сделал» не значит «дёшево». Поэтому неудачу прогона ловят по ФАКТУ
публикации вердикта (доехал ли до треда и до PR), а не по статусу джобы: зелёная джоба без публикации
— это потраченный прогон, а не успех.
